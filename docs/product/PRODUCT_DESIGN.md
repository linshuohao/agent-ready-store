## 1. 设计目标与资产入口

Agent接入分为 MCP 与 WebMCP。MCP Apps 是 MCP 的交互式 UI 增强，复用现有 MCP Server、连接和业务用例，不构成额外入口或路径。支持 Apps 的 Host 展示内嵌 UI；不兼容时降级为 MCP 文本与结构化结果。降级保留可用工具能力；购买仍遵循适用契约与Human确认要求，不能把文本返回视为完整购买验收通过。当前订单生命周期目标由网页订单入口承接无 Apps 时的Human支付，实际可用性须验证。验收覆盖 MCP 的 UI 增强与无 Apps 兼容模式，以及 WebMCP 页面工具。 业务承接见 [Requirements §3.3](REQUIREMENTS.md#33-当前需求agent交互形态的生单与human支付)。

让用户看清“仍在选购”“已有待支付订单”“已支付或关闭”，等待付款不阻塞继续购物，未知结果可以定位原单。沿用黑白极简、zh-TW系统文案、原商品文本保真和功能优先，不引入新视觉系统。

[统一设计预览](../../design/index.html)及既有截图是旧流程/视觉参考；新的行为和组件关系以本文及Technical Design §3～5为准，本轮未更新演示资产或执行页面验收。

## 2. 信息架构与页面职责

Web与Apps共用页面、流程、控件与视觉；依2026-10-31 Human进一步明确的展示约束，Apps只为搜索结果与最终结算生成卡片、内嵌主要区块上下排列且不显示搜索表单，商品结果卡片可按宽度并排，支付状态在同一卡片更新；不另设计Apps专用购物页面、摘要布局或控件。此限定已由Human明确确认并授权实施，详细架构统一见[Technical Design §5.2](../engineering/TECHNICAL_DESIGN.md#shared-commerce-application)。产品基线其余Draft状态及最终验收边界不因此改变。

| 页面/载体 | 内容与入口 |
| --- | --- |
| 列表/详情 | 沿用有界搜索、筛选、独立评论和公开可售量；普通Web加购轻量反馈，纯浏览不建车 |
| 购物车 | 持续车、逐项数量/移除、完整行勾选、所选金额预估、创建订单；提供独立订单列表入口，空车不隐藏入口 |
| 订单列表 | /orders?cartId=…集中展示该车待支付及历史订单；购物车和详情不嵌入列表 |
| 统一订单页 | /orders/{orderId}按待支付、已支付、已取消、已超时显示同一固定摘要；有效待支付提供Human模拟支付与取消，继续购物独立可用 |
| 分享订单页 | 仅该单固定摘要/状态及有效期内Human支付；不显示车、其他单或取消，不改变当前购物指针 |
| Apps内嵌载体 | 搜索展示一张结果卡片；购买准备不生成中间卡片，最终展示结算，Human支付及结果在同一卡片更新。共享页面继续支持卡片内主动导航，主要区块纵向排列，搜索商品卡片自适应并排且不显示搜索表单；不是另一套页面设计 |

旧/checkout/{cartId}、旧/orders/{cartId}及凭证链接提示进入新流程，不映射历史单或隐式购买。原视觉“五页”是历史资产范围，不要求为新订单状态新增重复业务页面。

## 3. 用户旅程与确认边界

普通Web：浏览 → 加购 → 改量并选整行 → 核对所选预估 → 创建待支付订单 → 审阅固定金额 → 点击「確認支付」 → 同单结果。创建成功选中行转出并直接进入原订单，动画提示已建立；支付/取消确认结果后提示、滚至页首并聚焦状态。未知或迟到结果保持原恢复与不抢导航约束；Demo不扣款说明保留。剩余车与其他单可继续操作。

2026-10-31 Human验收明确要求以上页面拆分、支付文案和操作反馈修订；不扩大交易规则批准范围。

Agent：咨询只读，明确加购只改车，明确购买在完整目标及预算/规格满足后直接生单。基础MCP返回网页入口，WebMCP导航订单页，Apps内嵌显示；最终均由Human点击UI模拟支付。Agent不能代点，UI不等模型后续消息。WebMCP明确加购通常展示车，要求留页时遵守；购买中的内部加购不插入车页，启用工具不跳页。

本人无当前车或同车时接续原车；有A车打开B订单先只看单，点击「繼續這次購物」才确认切换指针，不合并或删除A。分享始终不改变当前指针。没有主动新建/切换购物车来绕过配额的操作。

订单是固定审阅对象，不新增Review/签名/再次准备。价格变化不改有效原单；想改数量须取消并重新选购。未支付显示待支付，不能提前显示购买成功。

## 4. 核心交互与状态

| 状态/事件 | 设计表达和恢复 |
| --- | --- |
| 数量编辑/选择 | Enter或失焦保存，移除立即提交；首次全不选并可全选，有效选择页面内保留，新加行不自动选；未保存数量不能生单 |
| 问题行/空选择 | 目标行严格校验，问题行保留供删除/修正；未选问题行不阻止合法选择，空选择不创建订单 |
| 草稿/并发 | 有草稿不覆盖，显式刷新放弃草稿；同车写短暂协调，不排队合并或换版本重放；待支付单不锁全局 |
| 生单成功/失败 | 成功分别安装服务端订单与剩余车，不猜减行；失败整笔无新单/预留/转行，原输入可调整 |
| 价格预估变化 | 生单后显示实际固定摘要等待支付，不继续显示旧预估；订单后涨跌价不重报价 |
| 待支付上限 | 默认10笔有效待支付，满额说明原因并指向已有订单，可支付/取消/等待到期；不自动换车 |
| 15分钟到期 | 禁止发起新支付，显示期限提示并核实原单；本地到期不宣布已物化关闭，不覆盖截止前准入的迟到成功 |
| 支付未知/刷新 | 保留原orderId及未知标记，只读核实；一次CHECKOUT不能证明旧请求失败，不自动重付/重建，显式重试仍同单 |
| 取消/关闭 | 服务端确认关闭才显示取消/超时，释放不回车；已支付不能取消，不承诺退款 |
| 迟到/矛盾响应 | 车按cartId/version、订单按orderId/请求序号/终态隔离；迟到创建不抢页面，动作成功不被旧查询丢弃；矛盾终态禁用重复操作并重查 |
| 技术故障/目标不存在 | 区分不可用、未知、关闭和不存在，不伪装空车/零价；Host无法导航仍保留原订单入口 |

状态通过标题、文字和操作可用性表达，不只靠颜色。保留加载、空状态、明确失败及辅助提示；重要交互用繁体中文，不给用户展示事务/版本等实现术语。

## 5. 视觉规范（现有设计表达归档）

以下为视觉稿制作阶段在授权范围内细化、随现有设计归档的具体表达。Human 已接受黑白极简视觉方向，不据此虚构每一项像素值、字体或示意图的单独批准。实际样式维护于 [visual.css](../../design/mockups/visual.css)，表格说明设计意图，不建立另一套应用或大型 Design System；阶段归档也不授权实施。

| 项目 | 当前设计 |
| --- | --- |
| 语言 | 商城系统 UI 仅 zh-TW；原商品品牌/文本不翻译、不改写；无语言切换 |
| 字体 | 本机系统字体；优先 Apple 系统与 PingFang TC，Windows 回退 Microsoft JhengHei，再回退 sans-serif；不请求远程字体 |
| 正文 / 辅助 | 正文 15px、行高 1.75；常规辅助 12～13px；非关键商品示意标记 9～10px；不以小字承载金额、错误或确认条件 |
| 标题 / 价格 | 桌面主标题约 32～36px，手机约 28～29px；详情价格 28～30px；结账总额 21～22px；金额使用等宽数字特性 |
| 色彩 | 正文 #191919，次级 #595959，白底 #ffffff，轻表面 #f5f5f3，分隔线 #d6d6d6；主操作黑底白字，无渐变及装饰阴影 |
| 间距 / 容器 | 以 8px 为主要节奏，必要时 12/20px；内容最大宽度 1180px，桌面内边距 32px，手机 20px；采用层级留白而非堆叠卡片 |
| 栅格 | 桌面目录三列，移动两列；详情桌面图片/信息双栏，手机垂直；Checkout 桌面摘要/报价双栏，手机单栏 |
| 按钮 / 输入 | 主操作高对比，次级使用细边框或下划线；主要操作高度约 46～50px；输入有明确标签、可见边界和错误关联；禁用同时说明原因 |
| 卡片 / 图像 | 目录无额外阴影；商品示意在 1:1 轻灰区域，卡片外靠留白分组；图片不承载唯一商品身份 |
| 组件边界 | 统一 Header、商品卡、状态标记、规格表、评论、金额明细、Inline Alert、空状态和结果组件；Checkout 内容只读，数量管理留在 Cart |
| 圆角 / 焦点 | Web与Apps消费同一主题变量、控件及CSS，具体数值只在共享实现维护，不在Host覆盖；保留清晰深色焦点及减少动态效果支持，无需动效理解状态 |

## 6. 响应式与可访问性要求

视觉稿在 ≤850px 收紧留白，≤700px 进入移动重排，≤350px 的目录回退单列；这些数值是现有样式的设计表达，未来实现可在不改变重要体验契约时按实际内容调整。主摘要和金额不隐藏，不依赖横向拖动核对订单。设计方向接受不等于所有尺寸、缩放和设备均已验收，实际覆盖见第 7 节。

使用语义化 header/nav/main、连续标题层级、原生表单控件与可见标签、跳过导航链接、状态区 `role=status` 和重要异常 `role=alert`。商品图像有“示意、非实物照”说明，商品名称/ID/价格为独立文字。选择或错误不能只依赖颜色；焦点可见，不使用 hover 才能操作的入口。

未来实施验收需检查键盘路径、异常焦点定位、屏幕阅读器反馈、放大与文字重排、关键文字对比度及移动触控。实际检查范围与缺口见下节；源码包含这些机制不等于已完成全部无障碍验收。
