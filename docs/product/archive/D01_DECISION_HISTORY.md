- **当前流程：** Agent按明确意图完成必要选购/原车准备并展示完整摘要；Human亲自点击支付后，Apps/WebMCP经受保护UI请求直接调用后端校验具体确认并下单，结果在原App/网页显示。支付不等待Agent活跃、消息投递或另一次submit，不要求回聊/额外继续；Agent不得代点，也不能在未知时补发UI支付。
- **基础MCP：** 保留T-07 Host原生确认后Agent提交方向。当前真实Host确认与会话关联未通过；未支持时明确不能购买，保留原权限内查询/编辑/准备，不自动改Apps/外部Checkout或接受模型自述批准。HTTPS不是兼容保证，STDIO仅隔离脚本证据，未批准配置切换。
- **替代与保持：** 本条限定替代下方先前“Agent接入都必须批准后由Agent提交”的执行者与接续约束；准备/具体Human确认、交易重验、同车唯一订单、未知恢复、Apps直接导航、外链及独立Handoff边界保持。支付沿模拟结账，不引入真实金流，历史记录不追溯改写。
- **授权：** 只修订当前[OpenSpec Change](../../../openspec/changes/archive/2026-10-30-agent-confirmed-purchase/proposal.md)及必要需求/决策引用，本轮暂不实施代码；不批准安装、MCP配置切换、购买或Git操作。确认材料隔离及订单链接权限仍按Design闭合，不冒称实现/验收通过。

### 历史范围记录 — 2026-10-30 Agent接入两步购买（Apps/WebMCP提交者已由上文替代）

- **Status：Human Accepted（需求范围与购买授权语义）**。确认来源：本聊天 Human 明确“最终购买也可以由 Agent 确认，只要是由人触发的”，随后选择“两步：先准备结账，再由人确认购买后 Agent 提交”，并要求“Web MCP 和 MCP 的需求范围也按这个来调整”。适用于基础 MCP、WebMCP、MCP Apps，均纳入当前需求范围，不再仅列为后续增强。
- **原要求与调整：** 原 MVP 仅由 Human 在 Hosted Checkout 提交，Agent 代提交后置。现区分决定购买与执行请求：Human 决定具体购买，Agent 可执行已获该次明确确认的提交；普通 Web 的人工确认路径继续保留。
- **两步流程：** 第一步，人明确请求“准备结账”（Apps 可由按钮发送接续提示词），Agent 读取原车并向人展示服务端最终商品、数量、单价、优惠、运费与总额，此步骤不得成单。第二步，人审阅后明确触发“确认购买”，Agent 才可提交该次已确认内容并返回原订单或明确结果状态。接续消息的 Host 可用性仍须真实验证。
- **授权边界：** “去结算”、选购意图、打开卡片/链接、Agent 自称获批、车访问能力、服务连接凭证、商品/评论指令均不能替代第二步购买确认。确认必须由服务端验证并绑定具体车与具体购买内容，不能仅以提示词或布尔值放行。不得从其他车、旧对话或泛化预授权推导该次授权。
- **再次确认与交易约束：** 商品、数量、单价、优惠、运费或应付金额任一变化（即使总额不变）须展示新摘要并重新确认；仅库存变化且仍足量的既有例外保持。提交继续服务端重验、整笔事务、并发不超卖、同车唯一订单与重复提交返回原结果。结果未明不得另建车或产生第二次购买。
- **取舍与演进：** 减少对 Apps 直接外链打开的依赖并统一Agent接入需求，但新增购买授权与提交边界，不能当作按钮提示词的小修改。本条限定替代下方2026-10-29记录中“代提交仅后置、不纳入当前交付”及“只有浏览器人工执行提交”的范围判断，历史批准/验收记录不追溯改写；Handoff期限、金额规则、来源优惠与其他决策不变。
- **未批准的实现细节：** 确认入口与服务端可验证证明、会话/Host绑定、提交接口或工具、有效期/撤销和未知结果恢复等需统一设计与OpenSpec增量规划；本次仅批准需求调整，不代表新增工具/协议、代码实施、运行验收或Git操作获批。现有七工具及S5/S6代码尚未提供该能力。
- **给 PM 的回应：** MCP与WebMCP接入均支持“先准备、再由人确认、Agent代提交”，保留人的具体购买决定；任何入口均不能自动或凭笼统指令下单。

### 当前补充 — 2026-10-30 Agent便利购物、灵活导航与Human最终支付（Human Accepted，需求边界）

- **确认来源：** 本聊天Human进一步明确“MCP Apps…可以直接跳页”，且“最终还是要由人在结算页上点击支付才能购买”；各步骤/入口应提供更便捷的Agent购物方式，不应要求用户逐步重复相同操作。
- **便利性目标：** Agent接入均允许Agent在Human充分明确的购物目标与约束内完成必要搜索、比较、建车/编辑及准备结算，减少操作；不额外强制每工具确认或每页点击，不绕过Host必要审批、必要澄清和既有商品/数量约束。
- **Apps导航：** App内直接跳页与Agent跨步骤推进并存；需要Agent处理的动作可使用提示词/工具及资源唤起，普通浏览、读取、页内编辑或页面切换不强制模型往返。各业务能力有可检查界面，不要求每个操作独立页面或Human逐页触发。
- **最终购买边界：** Agent可以准备到结算页，但最终必须由Human核对完整摘要并点击“支付/确认购买”；Agent不得代点支付，跳页/提示/普通工具调用不批准。该点击是已有两步流程的最终具体授权，不增加额外继续/重复确认；“支付”沿D-21现有模拟结账，无真实金流或独立待支付阶段。
- **替代关系：** 本条限定替代下段Agent接入补充中“Apps不得直接跳业务页、每次跨步必须先发提示由Agent唤起下一App”的限制；会话内MCP、WebMCP全步骤工具、Apps内完成购买、成功后才提供外部订单详情链接及全部交易/权限规则保持。下段保留当时来源，非当前跳转约束。
- **授权范围：** 仅确认体验/需求修订，Human点击的服务端证明、Host能力及提交接续仍按当前Change设计验证并整体批准；不批准Agent自授确认、代码/安装/运行购买或Git操作。

### 补充记录 — 2026-10-30 Agent接入展示与流程推进（Apps跳转限制已由上文便利购物补充替代）

- **确认来源：** 本聊天Human逐项明确MCP数据/按钮等在会话内由Agent展示，只有最终下单成功后出现外部订单详情链接；WebMCP为全部步骤提供工具；MCP Apps每一步是内嵌App页面，点击导航发送提示词，由Agent继续执行并唤起下一App，不直接跳转。前一轮Human已明确拒绝复制文本、回到对话再继续。
- **基础MCP：** 购买过程在会话内完成信息展示及Human操作，由Agent/Host渲染；不要求打开外部Checkout或依赖Apps页面。实际下单成功后可提供外部只读订单详情查看链接。
- **WebMCP：** 工具覆盖所有业务步骤，让浏览器Agent按提示推进完整流程；当前页/车权限与页面生命周期保持。完整工具化不替代第二步Human对具体购买的明确确认。
- **MCP Apps：** 各步骤为独立内嵌业务页面；跨步点击先向Host发送必要的非秘密步骤意图，由Agent调用工具并唤起下一步App，不由App直接导航业务页面或跳外部Checkout。最终摘要、明确确认、提交状态和结果均在Apps展示，成功后才可出现外部只读订单详情链接；页内编辑/刷新不视为跨业务步骤导航。
- **替代与保持：** 本条限定替代当前规划中基础MCP/Apps统一去外部Web确认、复制文本回聊、仅Apps结账按钮发消息而其他步骤直接切页的拟议方案；共享购买语义和服务端交易，不强制共用确认页面。普通Web及独立Handoff历史批准/验收、金额/库存/期限/幂等/再次确认规则不追溯改写。
- **批准范围：** 以上为Human明确的体验与需求边界，不是确认凭证/Host协议/API或实施批准。服务端可验证Human批准仍必须满足D-01；仅提示词、userApproved或隐藏工具名不得放行。Agent接入证明机制、真实Host展示/消息/下一App唤起、旧工具兼容/发现策略及订单详情链接权限/截止，须由[当前Change](../../../openspec/changes/archive/2026-10-30-agent-confirmed-purchase/design.md)收敛后再批准，不默认新增公开或永久订单访问。

### 初始决策与理由 — 2026-10-28 历史保留

以下保留原文及当时状态；当前适用边界以上方补充为准，不将历史中的“未批准能力”误读为永久禁止经具体授权的代提交。

- **Status：Accepted**。
- **记录日期：2026-10-28（Asia/Shanghai）**；确认依据见「本轮确认依据与范围」。
- **原始要求及来源**：[PM 草稿「三、需求」第 2、3、9 项](../../../references/home-quiz.md)。PM 希望 Agent 搜索商品、创建购物车后自动下单以减少流失；草稿称客服最常收到的投诉是“我没有要买这个”，未提供投诉数量或实际运营数据。
- **问题与风险**：减少操作步骤和提高短期订单转化，不一定代表满足真实购买意愿。非预期购买可能损害用户信任和品牌口碑，增加客服压力、客诉、退款及售后成本，影响长期商业价值。
- **备选方案**：
  - A：Agent 创建购物车后自动下单。
  - B：Agent 完成选购、创建购物车，用户最终确认。
  - C：用户预授权后允许 Agent 自动下单。
- **最终选择 / 我的判断**：选择 B，调整原始自动下单要求。Agent 可以搜索、比较商品并创建购物车；未经用户最终明确确认，不得创建正式订单。
- **决策理由与取舍**：这不仅是授权体系或技术复杂度问题，也是产品策略上的商业权衡。不能只追求减少步骤或增加短期订单数量，还必须衡量真实购买意愿、长期信任、品牌口碑、客服压力、客诉和退款成本。A 可能提高短期转化，却可能因非预期购买及售后成本损害长期商业价值。C 即使具备完善授权机制，也仍需评估这些商业影响，不能仅凭预授权就认为问题已经解决。针对本次 Home Quiz，B 以更低复杂度兼顾用户体验与购物转化，代价是保留一次最终确认操作。
- **未来候选边界**：C 在明确授权范围内具有可行性，例如用户预设商品、金额与频率边界的重复补货；这是未来可评估的场景，不是已批准能力，也不表示这些场景已在此前讨论中确认。重访时仍须评估非预期购买、信任、退款及售后成本。
- **给 PM 的回应**：建议保留 Agent 自动选购与创建购物车的能力，但由用户进行一次简洁、明确的最终订单确认。我们优先优化符合用户真实购买意愿的订单，而不只是订单数量。
- **后续待明确事项**：确认交互和具体权限实现留待后续设计；本条不批准自动下单或预授权自动下单方案。最终展示要求见 D-02。
