设计思路：关键决策与执行分开

我们把目标、关键业务语义和高风险取舍留给 Human，把边界内可逆、可验证的实现交给 AI。讨论转入执行时，交接清楚决策、理由、约束、待验证假设和验收方式，避免执行者从长聊天中重新猜一遍。

平面在项目中的责任
Control明确目标、范围、有效契约与决策权，回答“应该做什么、哪些不能擅自改变”。
Execution按需获取上下文、探索和实施，回答“在这些约束下怎样完成”。
Evidence用测试、运行结果和审阅核对行为，回答“凭什么相信完成了”。

这三者持续配合，不是三轮审批。探索与决策、交付与验证是可以往返的两种循环；简单任务可以直接执行，复杂任务也只展开当前需要的切片。

沿着图讲一次任务

  1. Human Intent：先把目标说成可检查的结果

    明确要改变的行为、范围、非目标和必须保持的不变量。先理解全局旅程与依赖，再选一个能独立验证的小切片；这样既不漏掉系统约束，也不用提前设计全部功能。

  2. Workflow：准备最小充分的执行上下文

    按影响、可逆性、契约和验证能力选择路径，只读当前有效 Decision、Spec、相关源码与测试。实施前检查入口、依赖和真正的阻塞项；局部选择由 AI 自主，重要语义缺口才升级。

    决策交接和 Task Contract 复用现有记录，说明“依据什么、允许做什么、如何验收”，不另建一套计划。这样减少重复推导，也避免沿用旧方案。

  3. Explore / Design：用反例收敛关键未知

    目标或方案未明时，比较可行选择、代价与失败场景；能靠低成本实验回答的问题先验证。Human 确认关键取舍后，AI 在边界内推进，不因另一方案更优雅就不断重开讨论。

  4. Implement / Test：以可验收切片小步推进

    先看实际代码和已有测试，再进入“最小实现 → 真实验证 → 检查 Diff”的局部循环。普通实现细节无需逐项请示；遇到契约冲突就暂停依赖部分，不靠修改约束或降低断言让结果看起来正确。

  5. Behavioral Review：理解行为，再验证契约

    从相关入口追踪调用、状态、时序和副作用，对照已确认规则寻找最小反例。简单修改用静态检查和相关测试；高风险路径再增加 Trace、异常或并发验证，并按需独立审阅。

    源码推断、真实运行和未验证信息分别说明。测试全绿或 Reviewer 认可都不能单独证明正确，关键路径需要契约、代码和运行证据相互核对。

  6. Delivery / Learn：交付证据，让偏差回到正确位置

    交付变更行为、实际命令与结果、验证范围和残余风险，复用仍有效的审阅，不重复全部检查。实现缺陷回修复；假设被推翻时，按“原假设 → 证据 → 影响 → 建议变更”交回决策。

    合并需要相应授权；后续只沉淀重大决策、关键变更、有效回归测试和真实协作教训。流程本身若增加成本却没有减少缺陷或返工，也应继续做减法。

在本项目里怎样落地

Codex 与 Workflow Skill 负责路由和执行；OpenSpec 维护唯一正式 Spec、Design、Tasks 与变更生命周期；Superpowers 补充测试、调试等执行方法；Review Skill 提供横向审查。正式业务行为或重要变更使用 OpenSpec，普通局部维护直接完成，不叠加平行计划或固定审批阶段。

本页用于交付讲解，不是新增执行规则或产品验收证明。当前项目已搭建工作机制，尚未开始商城实现；具体规则与批准状态以项目入口、有效 Decision 和 OpenSpec 为准。
