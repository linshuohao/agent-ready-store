# Review Routing

作为项目的轻量 Review 适配器：选择审查方式、衔接反馈处理、组织帮助 Human 理解设计与实现的变更导读。统一任务入口仍是 ai-native-workflow；本 Skill 不回调它，不另跑一套通用代码审查。权限、正式契约及 Git 规则沿用根 AGENTS。

## 选择一次审查

核对实际范围（含相关未跟踪文件）、适用 OpenSpec/Decision、已有审查与验证证据，用一句话说明选择。风险决定审查深度，人的理解成本决定展示形式；文件数、Diff 行数及绿测不能单独决定降级。

| 当前需要 | 路由 |
| --- | --- |
| 局部、低风险、行为直观的维护 | 聚焦自查与相关验证；无需独立 Reviewer 或可视化 |
| 行为变化、重要功能或合并前需要代码审查 | 复用已安装的 `superpowers:requesting-code-review`，选择一次符合风险的只读审阅；可用 Codex Review 可作为替代，不叠加同范围全量审查 |
| 收到 Findings | 按需加载 `superpowers:receiving-code-review` 核实反馈，实现者修复并重验；Reviewer 默认只读 |
| 需求、交互或技术方案尚待判断 | 对照相关目标与拟议方案做聚焦 Design Review；标准按需读[产品、设计与交付契约](../../../docs/workflow/PRODUCT_ENGINEERING.md)，不套用已完成代码审查流程 |
| 准备交付、PR 或 Human 验收 | 复用匹配当前范围的审查/测试，处理未决项，再按下节组织变更导读；最终 Showcase 按上述交付契约核对，不重复完整 Code Review |

框架相关代码审查同时引用[框架实践](../../../docs/engineering/FRAMEWORK_PRACTICES.md)，核对开发前选用的资料、框架职责、既有封装复用及必要例外。共享UI须检查Hooks与异步生命周期。只将适用条目加入本次审查输入，不另启动最佳实践审查、不以Skill清单代替原始代码与行为证据；纯文档审查不加载无关框架知识。

派发时提供原始契约位置、准确审查范围及证据入口，要求审阅者自行核对；实现者总结只作线索。项目只补充当前相关约束：金额、库存、订单、权限、购买确认、幂等及关键竞态的适用不变量与真实运行证据，不复制通用质量清单。合理用户预期可以揭示 Spec 缺口，不能自动成为已批准业务契约。

确需独立判断时使用全新只读上下文；依宿主与现有授权派发，不逐 Task 自动启动代理。相关 Skill/工具不可用时说明限制，按授权做聚焦自查或交接，不能声称独立审查已完成。审阅本身不授权安装、外部操作或修改被审代码。

## 变更导读与 Human Review

默认顺序：实现与验证 → 代码审查 → 核实/修复/重验 → 必要的定向复核 → 变更导读 → Human Review。只复核受影响范围；高影响未决风险须补证或交 Human 裁决，不能用 Recap 或绿测冲销。只读审查请求止于反馈，不自动修复。

实现者在当前对话或 PR 提供一个阅读入口，复用同一 OpenSpec、最终 Diff 与有效证据，按以下顺序帮助 Human 建立整体认知：

- **问题与前后变化**：用具体场景说明原问题、修改后的行为及本批范围。
- **整体设计**：沿主要操作或数据路径说明模块职责、状态归属与协作关系；后续批次先定位于整体设计，再展开本批差异。
- **关键取舍**：解释影响方案的约束、选择理由和代价；沿用已批准设计时直接引用，不重新选型或编造历史备选。
- **关键实现关系**：按调用、数据流或依赖顺序串联少量关键源码入口，说明各自职责与连接方式，提供可核对的位置链接；文档/配置修改则说明对应规则与入口的关系。
- **验证与待决项**：把 Findings 放回相关设计环节，说明影响、处理结果、证据及剩余限制；已解决的普通问题简述，集中呈现真正需要 Human 判断的取舍。

这是阅读顺序，不是固定五段报告或新增审批阶段。局部直观修改可合为短段落；跨模块数据流、复杂状态或异步恢复难以讲清时加最小图示/前后对照，需要多视图或交互浏览才考虑 Visual Recap。已有事实直接复用，不为导读重新全量分析仓库或复制正式设计。只读审查请求仍交付 Findings，不自动扩大为实现或完整交付。

重要方案需要 Human 提前决定时，先讲拟议设计；实施后补实际差异与证据。导读完成不代表 Human 已接受，后续按疑问深入关键位置，无需逐行讲解。独立 Reviewer 仍依据原始契约与源码检查，不能只审实现者导读。

本次开发审查使用本地/测试环境证据；合并、发布部署后的生产检查交接后续部署验证，不阻塞已满足条件的开发验收与归档。导读区分已验证环境和生产待检查项；必要的真实数据库、并发或 Host 测试缺失仍须处理，不能以“部署后再看”替代。

Recap 基于稳定的审查范围、最终 Diff 和有效证据生成；独立代码审查仍读取原始契约/源码，不以生成摘要代替。后续修正只更新受影响视图；新风险再触发相应审查。图示中的事实需与实现核对，UI 示意不代替真实页面检查。可视化反馈产生缺陷时返回定向修复/重验，再更新视图。

需要 Visual Recap 时先确认 Skill/工具可用并读取实际说明；本 Skill 不安装或发布。默认优先 local-files 隐私模式，注意它不等于完全离线，托管 UI/模型的数据边界仍须核对；原件与机密遵守 AGENTS，外部发布须对应授权。未接入或生成失败时提供已核实的摘要/普通图示，说明缺口，不称已完成 Visual Recap；不阻塞已可交付且未被明确要求的展示增强。

## 状态留在已有载体

不建立审查状态文件、数据库或状态机。单次工作在对话记录；需跨会话交接时，将最小事实写入当前 Change 的 Tasks/证据段或已有 PR，不新建平行任务表：

- 对象：commit/range，或未提交 Diff 的可复核标识与文件范围。
- 审查：自查/独立、实际执行者和结果；未决 Finding 的位置、影响及处理进度。
- 验证：命令/环境/结果及证据入口，未执行或复用他人证据需明说。
- 人类审阅：变更导读入口、按需图示及 Human 待决事项；导读完成不等于验收通过。生产待检查项按 Workflow 的环境边界交接后续部署验证。

从这些事实恢复下一步，不只相信“已完成”勾选。对象、环境或契约变化时只使相关证据失效并补验；旧 Recap 不代表新改动已审查。审查通过、测试通过、可视化生成及 Human 接受分别记录，不能互相推断。

只读审查返回简短结论与少量可行动 Findings（位置、预期来源、触发/影响、证据及确定性）；交付则按上述导读串联成果、下一步与 Human 待决事项。无需逐轮报告文件。只有真实取得反馈才记为独立审查；本 Skill 不批准提交、归档、合并或发布。
