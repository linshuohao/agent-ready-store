# Spec Delta

## Purpose

使 Agent 能把同一购物车的有限访问能力交给无需登录的 Human，支持有效期内重复打开和编辑，并安全进入既有结算确认流程；固定首次分享期限，避免重试续期、跨车泄露或把访问能力误作购买授权。

## ADDED Requirements

### Requirement: 同车首次分享与完整报价

系统 SHALL 在有效车权限内为尚未完成的车生成 Handoff，分享同一 Cart Token，不新建车或第二份访问能力。结果 MUST 包含 CartView、可用时的完整分项报价、URL、首次签发时间、统一截止和 requiresHumanConfirmation=true；空车或受阻车保留问题提示，不将其标为可购买。URL 由服务端固定商城 origin 构造，不接受任意重定向目的地。

#### Scenario: 分享及受阻车
- **WHEN** Agent 对有效未完成车生成链接，包括库存随后下降或条目已为空的车
- **THEN** 返回原车、当前完整报价或不可报价原因及同车链接，Human 可接手调整；不预留库存、不生成确认或订单

#### Scenario: 完成后重新签发
- **WHEN** 车已成单后调用 create_handoff
- **THEN** 拒绝签发，不更改首次分享时间、订单或库存；有效权限内可用 get_cart 读取原结果

### Requirement: 首次分享的统一固定期限

系统 MUST 在同车串行化下，仅允许创建起24h未到期且未完成车首次分享，持久记录首次分享时刻，所有入口统一改为该时刻起完整24h。重复签发、兑换、读取、编辑、失败及重启不续期。截止等号即失效，过期不删除车/订单或补发权限；首次分享不延长已签发的购买确认材料。

#### Scenario: 并发首次分享与响应丢失
- **WHEN** 两个首次分享请求竞争，首次提交后响应丢失并重试或重启
- **THEN** 仅有一个首次时刻及同一链接；截止保持首次分享起完整24h，不随重试改变

#### Scenario: 锁等待跨创建截止
- **WHEN** 请求到达时未过期，但取得车锁并完成首次分享准入检查时已达到创建截止
- **THEN** 拒绝首次分享，不以请求到达时间或事务开始时间放行

#### Scenario: 原确认与新截止
- **WHEN** 首次分享前已取得确认材料，分享后 Cart 截止延后
- **THEN** 旧确认仍按原截止失效；需要新的确认截止时重新审阅，保留会话绑定、恢复栅栏及明确点击

#### Scenario: 与成单竞争
- **WHEN** 首次分享与同车购买提交竞争
- **THEN** 按同车执行顺序裁决；成单先完成则拒绝分享，分享先完成则购买按统一访问期限及原确认自身期限重验；同车仍最多一订单

### Requirement: 确认到期与车权限到期分离

系统 MUST 区分旧确认材料到期与购物车访问到期。确认到期只撤销旧材料，不证明车已过期；当前车权限仍有效时，系统 SHALL 提供重新审阅入口，展示最新摘要并等待新的 Human 明确点击。服务端已确认车权限到期才显示终止失效状态；技术故障或响应未知不得据此断言车到期或购买失败，不自动重发购买。

#### Scenario: 客户端确认计时到期
- **WHEN** 首次分享前取得的确认材料达到原截止，Cart因首次分享仍在新有效期内，浏览器仍持有效车权限
- **THEN** 清除旧确认、禁用旧购买按钮并提示重新审阅，不宣称购物车已过期；显式重新审阅成功后显示最新摘要，只有Human新点击才购买

#### Scenario: 服务端拒绝已过期确认
- **WHEN** 客户端计时未触发便提交旧材料，服务端最终准入时确认已过期而Cart访问仍有效
- **THEN** 以可区分的确认到期错误拒绝本次新购买，不成单、不扣库存；界面提供显式重新审阅，不进入仅能返回商城的车过期状态

#### Scenario: 重新审阅时车权限已失效或结果未知
- **WHEN** 确认到期后显式重新审阅，服务端发现车权限已到期、原车已成单，或请求发生技术故障
- **THEN** 分别显示车已过期、有效权限内原成交结果，或保留结果未明及安全恢复入口；不把技术故障伪装为到期，不重建车或自动购买，也不因确认到期清除既有未知购买标记

### Requirement: fragment 兑换与秘密隔离

系统 SHALL 从 Checkout 链接 fragment 取得车 Token，先从地址清除，再以受同源防护的 JSON 请求兑换每车 HttpOnly Cookie；只兑换已有有效且已分享车的能力，不创建或续期，不签发购买确认。系统 MUST 拒绝畸形/错车/过期 Token、冲突凭证和 URL query 传秘密；秘密不进入日志、RSC、共享缓存或持久客户端存储。

#### Scenario: 无 Cookie 的首次接手与重复打开
- **WHEN** 新浏览器打开有效链接，或另一次打开同一链接
- **THEN** fragment 被清除后兑换同车 Cookie，展示原车来源、内容和金额，再走现有独立审阅；不登录、不自动购买、不延长截止

#### Scenario: Cookie 冲突与兑换响应丢失
- **WHEN** 同车已有不同 Cookie，或兑换响应丢失而结果未知
- **THEN** 冲突明确拒绝；未知时保留内存原材料供显式重试，不据此新建车；刷新且 Cookie 未到达时引导重新打开原有效链接，不把 Token 写入存储

#### Scenario: 切车与地址安全
- **WHEN** A 车兑换响应迟于切换至 B 返回，或地址含非法 fragment/query
- **THEN** A 响应不更新 B 的摘要/当前车/确认；非法输入无权限提升，错误不回显秘密，fragment 不转发到服务端或其他页面

### Requirement: 接手编辑与失效反馈

系统 SHALL 兑换成功后选择原车，沿用既有 Cart 编辑与 Hosted Checkout；Human 编辑不改变 AGENT 来源或优惠资格。系统 MUST 在链接失效时显示独立失效状态与重新购物入口；技术故障与过期可区分，完成车有效期内显示原订单。打开链接、兑换和编辑均不构成购买授权。

#### Scenario: 编辑和明确确认
- **WHEN** Human 通过有效链接接手、调整数量并返回结算
- **THEN** 保留原车与可信来源，重新审阅最新完整摘要，等待 Human 明确点击，原子保存唯一订单并扣库存

#### Scenario: 到期与技术失败
- **WHEN** 兑换发现过期或遇到服务不可用
- **THEN** 分别显示无法继续使用原车的失效说明或可重试的技术反馈；不自动重建、不补发期限；桌面/移动键盘及辅助反馈可用
