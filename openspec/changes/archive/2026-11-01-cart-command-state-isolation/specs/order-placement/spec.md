## MODIFIED Requirements

### Requirement: 原子创建待支付订单
系统 SHALL 从有效cartId、原创建请求键及selectedItems的productId/quantity创建全局唯一orderId，初态CHECKOUT，记录来源车、创建通道和固定快照。quantity为购买量；不接收expectedCartVersion或expectedQuantity，不要求车行存在或数量匹配。按请求量校验完整目录、库存及约束；所购SKU当前车行整条删除、车版本递增、订单和预留同时提交，不创建Checkout/Review实体，Order.cartId必填且允许多单。sourceCartVersion仅为服务端事务观察值，不作购买前置条件。

#### Scenario: 合法选择和完整约束
- **WHEN** 明确购买清单包含数量和预算、币种、规格等限制
- **THEN** 按请求量验证完整集合及限制并纳入幂等载荷；车量不同或无对应行不阻止购买。任一ID重复/非法、商品不可购、库存不足或约束不符整笔拒绝，不静默少买、拆单或改约束；未选问题行不阻止合法清单

#### Scenario: 生单故障
- **WHEN** 订单、明细、预留或车清理任一步失败
- **THEN** 全部回滚，原车及可售库存保持，失败不留下部分订单或成功幂等事实

#### Scenario: 购买数量与购物车清理分离
- **WHEN** 买A×2，当前车有A×5、A×1或无A，库存及其他约束满足
- **THEN** 订单都固定A×2，当前A记录若存在则整条删除，不保留差额；无匹配记录也成功，新订单事务递增一次车版本

### Requirement: 创建恢复与独立多单
系统 MUST 按cartId和createOrderRequestId持久幂等，同键同载荷优先恢复原orderId及当前状态、快照、截止和当前车，再检查新请求配额/库存；同键异载荷冲突。恢复不再清理车。不同请求键代表不同购买尝试，车版本不用于去重；在库存/配额允许时可分别成功。后续车编辑或其他订单支付/关闭不改变本单金额、明细及状态，不使用车级结算锁或确认epoch。

#### Scenario: 同键重启恢复
- **WHEN** 成功生单丢响应，车中已重新加商品、价格变化或服务重启后恢复
- **THEN** 返回原单及当前车，不重算、不再预留、不重放车清理；原单已支付或关闭仍返回该事实，不复活

#### Scenario: 不同键竞争和后续购物
- **WHEN** 同车两个不同键并发购买相同商品数量，或原单待支付时继续购物
- **THEN** 库存/配额允许时两个不同键都可成功，各自固定快照和预留；不因相同清单或车已清空推断重复，不自动生成第二键；后续订单独立

## ADDED Requirements

### Requirement: 生单尝试与局部清理
系统 MUST 在发送前按请求键保存冻结购买清单、约束、通道及本地代次。成功保存orderId后，仅清理仍属于该尝试的选择/草稿和未决记录；车快照按cartId/version安装，不在响应到达时再次按SKU删本地行。未知保留原请求，默认提供只读查询结果，继续原购买需另行明确选择，不推测已清车，不自动重建；其他购物可继续，同次尝试不能换键重复购买。

#### Scenario: 生单后同SKU重加且响应乱序
- **WHEN** 生单事务成功后A重新加购并产生新草稿，原生单响应才到达，B未被购买
- **THEN** 记录原单，保留后来A、新草稿及B；低版本车响应不覆盖高版本，只结束原尝试拥有的状态

#### Scenario: 两种并发清理顺序
- **WHEN** A加购先于生单提交，或生单先于A加购提交
- **THEN** 前者生单按清单数量购买并删除当时A整行，包含先提交的追加量；后者后来A保留。B不受购买A的SKU清理影响

#### Scenario: 未提交的未知请求遇到新车状态
- **WHEN** 原请求未提交，车数量变化或所购行已不存在，用户明确恢复原购买
- **THEN** 按原清单重新校验当前目录库存预算和配额，可以生单并清理当前同SKU整行；说明恢复可能执行写入，不因车变化报版本冲突，不伪装为只读查单

#### Scenario: 切页与本地存储失败
- **WHEN** 成功响应晚于切页，或保存orderId关联时本地存储失败
- **THEN** 不抢导航；先保存成功关联再清原pending，失败保留恢复依据和已知成功提示，不误报购买失败或自动重建

#### Scenario: 取消到期及支付独立
- **WHEN** 原单取消/到期或Human支付，而车已有后续商品
- **THEN** 只处理原单及其库存归属，不回车、不清后续意图、不比较当前车版本

### Requirement: 生单结果只读查询
系统 MUST 支持按cartId及原创建请求键只读查询已提交订单；找到返回原orderId及当前订单事实，未找到仅表示当前未观察到成功，不证明失败、已取消或原在途不会提交。查询不调用生单、不清车、不预留/释放库存、不触发请求到期扫描、不延长期限；技术错误不能转为未找到。保留既有入口认证及同源保护。

#### Scenario: 查询已成功与未提交
- **WHEN** 原生单已提交但丢响应，或尚未提交，用户点击查询结果
- **THEN** 前者返回原单，后者返回暂未查到；两者都不执行购买或清车，未找到保留原未知请求，不自动继续、换键或付款

#### Scenario: 查询与原生单交错
- **WHEN** 查询未找到后原在途请求成功，或旧未找到响应晚于已知成功
- **THEN** 原请求可独立完成，查询不承诺取消；客户端保留成功事实，后续查询同键找到同单，不能降级成未知

#### Scenario: 独立继续动作
- **WHEN** 用户明确选择继续原购买而不是查询结果
- **THEN** 展示原冻结清单及清理含义，并以原键原载荷发出写请求；未提交可按当前库存及约束完成购买，已提交只返回原结果。之后的移除或改量不得偷偷改写原载荷

#### Scenario: 旧契约退出后的未知请求
- **WHEN** 所有旧写入口已停止接收新写且旧在途已确认排空，随后核实旧请求
- **THEN** 只读返回已有成功事实或暂未查到，不执行旧载荷；无记录由已确认排空的切换说明告知旧流程未完成，用户明确重新购买才采用新契约。未证实排空时保持未知，不能凭未找到就换键重建

#### Scenario: 生单在途选择变化
- **WHEN** 提交A后新增选择B，或将A取消再以相同数量重新勾选，随后原生单成功
- **THEN** 前者仅清原A并保留B，后者保留重新选择的新A；按逐项选择代次判定，不按整清单代次整批清空或整批跳过
