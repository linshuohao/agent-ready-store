# Design

## Context

动机与授权见 [Proposal](proposal.md)。本方案基于 `Catalog.search` 的分类原值精确匹配、`CatalogService` 的共享查询、MCP Adapter 工具注册及普通 Web 的 `SearchForm`。现有分类/品牌为输入框，`CatalogPage` 在 embedded surface 隐藏表单；Web 首页通过 publicApi 加载商品。现有测试在 `apps/api/test/catalog/catalog.test.ts` 和 `apps/api/test/mcp/mcp.test.ts`，后者有工具全集断言，需要同步增加新工具。

约束来自现行 product-discovery Spec、D-15/D-19/D-20；Requirements CAT-01～04、Product Design 的共享表单/Apps隐藏约束、Technical Design §1共享用例提供背景。它们当前的Draft状态不构成本次新增行为获批。Human已审阅并批准本方案；复核后确认的分类入口到期清理豁免亦已批准。

## Goals / Non-Goals

**Goals:** 用一份真实分类数据服务 Human 和 Agent；发现查询不依赖库存数据库；兼容已有精确筛选和单卡片展示。

**Non-Goals:** 品牌选择器及联动、商品数量统计、查询相关分面、分类层级/翻译、新排序、WebMCP新增工具、向量索引和服务端模型。WebMCP继续使用既有搜索工具；普通页面下拉框对所有页面使用者可见。

## Decisions

### 1. 复用目录查询，不增加分类数据源

在 Catalog 提供分类投影，CatalogService 暴露不调用库存读取的方法。非空判定使用trim后长度，但输出和去重保留原字符串，不改变原件、不把简繁不同值合并。使用显式字符串比较保持跨环境排序确定，不使用依赖环境locale的排序。

采用派生分类而非手工配置枚举，避免目录与工具/页面漂移；不返回代表商品、描述、数量或价格范围，减少第一版语义与同步成本。分类文本按不可信纯文本处理，不作为Agent指令或HTML。

### 2. HTTP/MCP共用轻量分页契约

- HTTP：`GET /api/v1/catalog/categories`，避开 `/products/:id` 路由。
- MCP：`list_product_categories`，声明只读且不附加Apps UI资源；复用既有Result、可读结果和工具错误包装。
- 输入：offset非负整数，默认0；limit为1～100，默认50；catalogRevision可选，offset大于0时必填。拒绝额外字段；HTTP数字字符串沿用明确解析规则。
- 输出：`Page<{value: string, label: string}>`。复用Catalog现有对外revision语义（当前包含目录与匹配规则版本）；因此匹配规则变化也可能使分类续页失效，这是兼容性取舍，不增加新版本系统。
- 首次请求也校验传入版本；不匹配为CATALOG_CHANGED。库存变化不改变分类内容。错误沿用现有VALIDATION_ERROR与技术故障投影，不捕获后返回空数组。

分页复用既有Page约定，避免将分类数增长转化为无界工具输出；不创建缓存服务、分类表或搜索引擎。新增分类HTTP路由仅GET/HEAD（含Express默认大小写及尾斜线等价路径）豁免请求到期清理；MCP仅list_product_categories豁免beforeToolCall，认证和输入校验照常执行。其他入口仍按已批准vercel-demo-request-expiry增量清理。分类不提供库存或可购性，因此豁免不影响库存保守性。HTTP维持既有公开目录读边界，MCP维持服务认证及Host/Origin边界，不新增权限范围。

### 3. Web下拉框复用该接口

Web首屏并行获取商品和分类第一页，二者结果分开处理，分类失败不覆盖已成功的商品响应。共享CatalogPage/SearchForm增加显式分类结果输入，普通Web使用原生select与既有样式；embedded不额外查询、不显示表单。后续页通过现有Web API代理/客户端封装读取，不在浏览器放服务Token。

下拉框包含“全部分类”和已加载选项；仍有下一页时在控件旁提供“加载更多分类”，避免静默遗漏，也不为当前小目录建立完整可搜索选择器。请求进行中防重复追加；切换版本/重新加载时拒绝迟到旧页覆盖新列表。失败显示重试及仍有效的已有选项，不静默退回自由输入框。

URL里未加载或已消失的值保留为临时当前选项，标注“当前条件（未在已加载分类中）”；加载到同值时去重并去掉标注，不凭第一页缺失判定分类不存在。加载失败时也保留原值，提交其他条件不会丢失category。选择“全部分类”是用户显式清除。提交沿用现有表单的分页重置、URL及前后退恢复；分类选项的value必须原样编码，不能沿用当前表单对所有字符串trim的逻辑，否则含边缘空格的真实分类将无法精确匹配。

界面示意：`商品分類 [全部分類 ▾]`；品牌维持输入框。小范围控件变化用此示意和真实浏览器验收即可，不生成独立视觉稿。

### 4. Agent按需发现，语义解释仍由调用方负责

工具描述给出“不了解目录分类时探索；明确需求直接搜索”的指引。发现只提供可用词汇，不保证Agent理解任意语言或用途；对于歧义可澄清，随后用query_products/get_product核验。最终浏览展示仍由一次search_products完成；本工具不能作为最终商品结果。工具说明的质量通过真实Host案例验证，服务端无法强制模型遵从全部对话策略。

## Risks / Trade-offs

- 分类粗糙或用户描述仍模糊 → 明确这是词汇发现，保留澄清与详情核验，不宣称已解决任意语义搜索。
- 目录中有售罄分类 → 保留目录完整性，工具说明不承诺可购性；实际搜索/详情读取当前库存。
- 下拉选项随目录变化 → URL值保留、版本错页重置、显式重试，防止静默放宽条件。
- 类目增长 → 有界分页可继续工作；数量达到影响使用的规模后再评估可搜索选择器，不提前引入组件依赖。
- 新工具影响严格工具全集测试 → 更新相关断言并验证新工具无卡片、旧搜索UI关联不变。

## Migration Plan

无需数据库迁移。批准后先增加共享契约与只读接口，再接入页面；部署时先API后Web，旧客户端仍可使用既有搜索。回滚先恢复页面，再移除新增工具/接口，不涉及交易数据回滚。批准前不改正式Spec或整体基线状态；验收后的同步/归档遵循既有OpenSpec流程。

## Future Evolution

Human于2026-10-31明确将语义／混合搜索保留为后期演进方向；这不批准向量数据库选型、依赖安装或实施。后续评估由真实检索失败触发：目录确有适合商品，但分类发现、别名与关键词仍无法召回用途/场景相关候选。

先固定包含明确型号、多语言、模糊用途、预算、负面约束和无合适商品的查询集，由Human确认相关商品与硬约束。对比当前方案与关键词+向量混合召回，观察Recall@k、前k项相关性/误推荐、硬约束违规、延迟和每次成本；阈值与可接受权衡在实验启动前确认。没有适合商品时不以强行返回结果计为成功。

若收益明确，再提出独立Change，评估嵌入模型、多语言效果、目录增量同步、存储方式与排序契约。现有PostgreSQL扩展或独立搜索引擎都是待评估选项，不预先选择；语义召回不替代预算/品牌/可购性过滤和商品规格核验。RAG不要求向量数据库，现有检索+详情已能为生成回答提供事实。

动态分面计数和品牌联动同样作为按需后续增强，不列入本期实施Tasks。

参考实践（设计参考，不构成对本项目的效果验证）：[Meilisearch分面搜索](https://www.meilisearch.com/products/faceted-search)、[Typesense自然语言查询与字段枚举](https://typesense.org/docs/guide/natural-language-search.html)、[ShopTalk对话式分面搜索](https://arxiv.org/abs/2109.00702)。
