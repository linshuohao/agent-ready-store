# Design

## Context

状态为审查修订中规划，动机/授权及前序Change依赖见[Proposal](proposal.md)。Human已选定同一卡片按目标分组；本轮已授权在审查发现修复后提交实施，SDK升级和新协议支持也已明确授权。

观察：Catalog.search只接受单q，按空格拆词并全部匹配；normalize仅NFKC与小写；category/brand精确匹配；排序为推荐分数降序、ID升序。search_products/query_products复用同一服务，只有前者关联UI。Apps Bridge目前解析单Page，当前共享CatalogPage及导航也只携一组查询。目录约30商品，无需另建检索基础设施。

约束：继承Requirements CAT-01～04及D-14/15/19的有界公开投影和推荐排序；Technical Design §5的共享commerce-ui及HTTP/Bridge适配不分叉。本Change只新增搜索语义，不修改金额、库存占用、订单、身份或Human支付。前序结算Change尚未同步正式Spec，不能据旧正式文案恢复退役工具。

## Goals / Non-Goals

**Goals:** 一次表达完整的多个搜索目标；对明确登记的中英文术语和简繁输入得到稳定匹配；所有目标（含空/失败）在一个结果卡片出现；具备独立分页、去重、错误和恢复的可验证契约。

**Non-Goals:** 无限制全文语义搜索、任意语言机器翻译、错别字模糊召回、个性化排序、服务端搜索Session、向量库、购买合并或新增支付入口。本轮不新增普通Web多目标编辑表单或WebMCP批量页面工具；其既有单查询仅复用语言匹配。UI复用共享组件，不为Apps重建商品页。

## Decisions

### 1. 批量目标是并集，目标内条件是交集

采用{queries:[...], catalogRevision?: string, searchRevision?: string}与旧单查询结构互斥的严格联合schema，拒绝两者混传及未知字段。queries 1～5组；每组id为1～64字符的ASCII字母/数字/下划线/连字符且批内唯一，label可选1～80字符，q默认空且≤200字符。空q仍受该组筛选及分页限制；默认标题取label、非空q或「全部商品」。label只是纯文本，不参与查询、不允许当商品事实。

两个版本字段均位于批量请求顶层（非queries组内），长度1～128；任一组offset>0时两者必填，首页携带版本也必须校验，拒绝不匹配。运行时保持严格联合；MCP tools/list发布的inputSchema根必须为type: object，并以对象根内的anyOf/oneOf表达两种互斥形状，不能直接发布只有根anyOf的Zod联合输出。通过升级后的真实SDK client.listTools消费验证。

每组复用现有category、brand、minPrice、maxPrice、purchasableOnly、sort（仅recommendation）；offset保持已有非负安全整数规则，limit默认4、范围1～10。组间不继承任何隐式全局条件；Agent须将用户共用限制明确传播到相关各组。超过5目标拒绝，Agent先请求用户选择/明确分批，不能悄悄忽略。

示例请求：
```json
{
  "queries": [
    {"id":"earphones","label":"耳机","q":"蓝牙耳机","maxPrice":2000},
    {"id":"bottle","label":"水杯","q":"保温杯","maxPrice":1000}
  ]
}
```
结构化category/brand必须先确认是目录真实规范值；若不确定则仅用q查询并核对规格，不自行捏造筛选值。省略预算表示未指定，不等于任意购买授权。

为什么：现有q中拼接「耳机 水杯」会变成错误的AND；单一OR表达式又无法给每类绑定独立预算。独立目标是满足需求的最小扩展，不引入DSL。

### 2. 保持单查询兼容，批量数据一次投递

HTTP新增只读POST `/api/v1/products/search`（路径在实现前核对现有路由冲突），使用JSON及既有输入/Origin规则；GET `/api/v1/products`和旧单目标响应不变。MCP两工具都支持同一个严格联合输入：旧模式输出原Page，新模式输出如下形状，外层继续现有Result包装：
```json
{
  "kind":"grouped",
  "catalogRevision":"…",
  "searchRevision":"…",
  "groups":[
    {"id":"earphones","label":"耳机","query":{"q":"蓝牙耳机","maxPrice":2000,"offset":0,"limit":4},
     "status":"ok","productIds":["P001"],"total":1,"nextOffset":null},
    {"id":"bottle","label":"水杯","query":{"q":"保温杯","maxPrice":1000,"offset":0,"limit":4},
     "status":"empty","productIds":[],"total":0,"nextOffset":null}
  ],
  "products":["此处为现有ProductSummary对象；示例占位，不是实际schema"]
}
```
实际schema products为ProductSummary[]，groups.query回显全部规范化后的条件（不回显内部匹配索引），ok/empty/error为判别联合。ok允许offset超出末页时productIds为空但total>0，显示返回上一页；empty仅total=0。error提供公开code/retryable，无total/nextOffset/productIds，不伪造查询结果。products按groups顺序及组内顺序首次出现去重，组内ID唯一且全部能解析；同名不同ID保持独立。

组内排序仍沿用原推荐分数，分数不进入DTO。跨组同商品在每组保留展示引用，让用户理解关联；不是跨组强行归属首组，也不累计数量。最终展示由服务端重查条件，不能接收Agent任意商品对象、价格或HTML；因此后台探索与最终展示间库存可能变化，要展示最新读取事实而非宣称原快照。

### 3. 文字规范化与别名是共享的确定性匹配步骤

查询与目录的name/brand/category/description采用同一路径：NFKC → 小写 → 简繁规范化 → 匹配词项。展示仍使用原文；不改references或商品事实。英文别名按词/短语边界识别，中文采用登记短语的最长匹配，未命中剩余文字保留为字面词项；一条查询中词项之间AND，同一概念的登记别名之间OR。长短语不能拆散为过宽的独立词匹配，别名不递归扩展。

词表为受控项目数据，不从商品评论/用户指令动态学习。第一批最低验收概念包括「蓝牙／藍牙／Bluetooth」「水瓶／water bottle」「移动电源／行動電源／power bank」；需以合成商品夹具验证，不为凑匹配改原始目录。不自动将「水瓶」等价为「保温杯」，也不将「耳机」等价为其全部子类。未知词、型号、数字不能删除；不承诺任意中英文翻译。

优先采用可离线运行的成熟简繁转换能力，固定规则/版本，避免自己维护不完整汉字转换表；实现前以当前中文商品术语、歧义字及混合英文验证质量，检查依赖大小/许可证/构建兼容，再说明实际收益并确定依赖。不在本规划安装包，也不以某个尚未实测库已获批准。别名词表采用小型显式映射，禁止引入独立搜索服务。

品牌/分类结构化筛选仍精确匹配规范值，价格边界不变；多语言只改变文字召回，不把产品满足搜索等同满足购买规格。与引入模型翻译或向量检索相比，此方案可重放、可测试、无额外网络/服务，代价是词表之外的跨语言召回有限。

### 4. 版本、有界分页与错误

每批只读取一次公开目录和当前可售投影供各组复用，不为每组各读一遍库存；不创建锁或持久化结果。catalogRevision仍标识目录事实；searchRevision由匹配实现版本、简繁规则及别名内容共同决定。批量首请求可不带版本；任何offset>0的续页必须带响应中的两个版本。例如{queries:[{id:"earphones",q:"蓝牙耳机",offset:4,limit:4}],catalogRevision:"响应值",searchRevision:"响应值"}。单查询继续使用原catalogRevision字段，但其生成纳入匹配规则版本，以使旧客户端也不能拼接不同规则的页。

Apps某组翻页/重试通过query_products只请求该组及两个版本，返回后按组ID和请求序号合并。保留当前各组页，不无限追加；全卡最多5×10个商品引用，产品摘要按当前引用重建去重集。若同ID新读取摘要更新，所有引用统一更新并标为最近读取结果；不声称不同请求所得组是同一库存快照。库存变化下可购筛选仍可能导致跨页重复或遗漏，沿用原Spec边界，提供该组从首重查。

目录或searchRevision冲突使整张卡片标记需刷新完整集合，不拼接新旧版本。请求结构不合法、共享目录或库存读取失败为整批错误；仅在可明确归因到一个目标的已知可重试查询错误时返回error组并保留其他组。实现只有全局故障来源时不人为制造局部成功；未知程序异常正常上报，不能宽泛catch成无结果。全部组error时外层技术失败并保留公开目标诊断，不宣称展示成功。

### 5. 一张卡片的交互与恢复

复用CatalogPage的共享商品卡片，增加分组结果模式，不复制页面。区块按目标顺序上下排列；组内紧凑网格，保留各组标题/条件/数量/无结果或错误提示与分页。初始每组4项让一张卡片可同时包含所有目标；允许纵向滚动，不承诺全量结果一屏容纳。最终细节与另一个工作区的紧凑卡片修复对齐，未合并前不得假设其已生效。

搜索集合上下文保存完整查询和每组offset/limit、两版本，详情返回复用原上下文；借用现有Host稳定调用ID及sessionStorage适配，不新建服务端ID或通用状态管理层。重挂载有合法上下文时重查，不持久保存库存作为权威值；无上下文明确请求重新搜索。新工具投递沿现有草稿/在途协调，旧集合或旧组响应不抢新视图。

首次新意图可展示一次；组内操作只走无UI查询。后台比较可多次，最终批量search_products返回一个结果。Host仍可能因模型误调多次展示工具产生多卡，不能在服务端凭空合并历史卡片；工具说明、schema及真实Host用例共同验收，若失败先记录调用链，不能承诺仅靠提示词保证一次。

### 6. 候选商品结构化选择：优先点选、保留对话降级

**范围与入口。** 建议增加只读MCP工具`resolve_product_choices`（名称为本提案建议），不关联Apps资源，不把弹出选择隐含加入search_products/query_products。用户只是浏览多个候选时正常返回分组结果；只有明确选型/加购/购买目标仍存在必须由用户决定的型号歧义，且用户未授权Agent自行按明确标准选型时才调用。用户已指定SKU不重复询问；只有一个候选也不能将“搜索”变成购买。数量沿用户原目标，不让选择字段擅自改变数量。

该工具使用完整queries、每个目标必要的显式选型约束，以及可选的按组ID映射的用户已答复商品ID；这些都是待校验输入，不是审批凭证。服务端从当前目录重新取候选、详情及可购状态，选项只用真实productId，展示名称/型号/品牌/价格及区分所需规格。传入的自然语言或商品文本不生成可执行schema指令。每个未决目标单选一个SKU，最多5个目标，单目标候选上限10；这是工具的选型能力，不限制用户以后明确另买多个型号。

**三种结果。** 服务端返回显式kind：`selection_resolved`包含完整目标和按组选择的ID；`selection_required`包含各组候选及原因（unsupported、timeout、transport_unavailable、needs_narrowing、stale_selection等）；`selection_cancelled`区分decline/cancel。保留零候选、受阻和已明确目标，不能把部分选择伪装成完整集合。候选超过10时要求先缩小条件或在分组结果浏览后明确SKU，不把前10名伪称全部可选项；零可用候选不弹空表单、不自动换目标。无需新建搜索/选择数据库实体。

**点选过程。** 多个未决目标尽量在一次表单中呈现，用扁平字段choice_1…choice_5映射内部组ID；仅使用当前协商版本实际支持的字符串枚举与标题/描述，不能假定任意嵌套schema或富卡片可用。不预选默认型号、不收集密码/服务Token/支付资料。具体弹窗、表单或其他交互由Host决定。显示摘要必须足以辨别同名SKU；Host不能可靠显示区分信息时转入明确的对话澄清。

接收accept后校验必填字段、枚举成员、组对应关系及原查询约束，再读取最新商品/库存/价格；失效选择返回stale_selection，不偷换型号、不沿旧价继续、不自动循环弹表单。等待Human期间无数据库事务、锁、库存预留或购物写入；每次工具调用最多发起一次表单，decline/cancel立即停止此选择流程，不转对话强迫继续。超时/断连/协议不支持时返回可恢复的待选择状态，不能自动重发表单；用户明确继续后才再请求。

**降级与恢复。** 无协商能力时直接返回selection_required及公开选项，Agent逐目标请用户明确ID/型号，避免仅凭不唯一名称定位。下一次调用提交原目标和答复ID，服务端重新校验当前事实；客户端/模型声称“已点选”不构成可验证的Human授权。这里沿既定Demo信任边界，不新增身份凭证，也不重新引入已由T-09替代的Review/原生最终付款批准。工具响应丢失时不自动重放一次交互请求；可退回明确对话答复流程，不能因此建替代订单。

**接续购买。** 选择工具只解析目标，不直接改车、生单或支付。只有用户此前明确要求购买且完整目标均已解决，Agent才按现有幂等购物/生单工具继续准备，最后仅create_order展示完整结算卡片，Human亲自点击支付。此前仅搜索/比较时，选型结束仍只返回选择结果；不自行扩大授权。整个过程可有Host原生选择表单，但不额外产生商品/购物车Apps对话卡片；该表单不计作汇总结果卡片。

### 7. 协议能力与实施前置验证

2026-10-31实际读取：仓库@modelcontextprotocol/sdk为1.32.2，本地类型有Server.elicitInput/getClientCapabilities，协议常量最高2025-11-25；当前adapter每个POST新建Server，sessionIdGenerator为undefined且enableJsonResponse为true。代码审查证实：initialize的客户端能力只存于当次Server，后续POST无法继承，JSON模式也没有旧式服务端请求往返，因此现状不能直接完成原生选择。不能凭工具目录判断客户端能力。

外部依据：[TypeScript v2 elicitation](https://ts.sdk.modelcontextprotocol.io/v2/servers/elicitation)说明form及客户端能力检查，并明确2026-07-28连接不能照旧调用elicitInput；[Ruby SDK说明](https://ruby.sdk.modelcontextprotocol.io/server/elicitation/)解释新生命周期把交互请求放进input_required结果。它们提供协议方向，不是仓库1.32.2的直接代码模板；不同语言SDK能力不互相证明。

实施先做不含购物写入的兼容实验：分别记录现代server/discover及每次请求envelope、旧协议initialize与已有调用，验证版本协商、form请求关联、accept/decline/cancel及断连。真实Host与SDK测试分别记录；旧式原生往返不在本轮承诺，不为此新增持久会话。

Human于2026-10-31明确要求「我们要支持新协议，不要只支持旧协议。仓库SDK的版本也要更新」，在审查后提交实施授权上追加SDK升级与新协议支持。2026-07-28及其input_required续调为本次必须实现的契约，不得仅以旧协议或对话降级交付完成。

采用官方v2拆包（server/core/client当前正式发布2.4.0、Node适配当前正式版以registry核实并锁定），使用createMcpHandler及Node适配，保留无状态HTTP和同一/mcp入口，显式支持现代请求与旧stateless调用。新协议读取每次请求的SDK envelope能力；不在工具参数内自报、不跨客户端缓存。SDK升级本身不等于启用新协议，必须验证server/discover、版本协商、tools/list/call、resources/read和input_required续调。旧协议保留查询/购物/Apps兼容；旧客户端无可验证交互通道时明确对话降级，不为旧式原生弹窗新建持久会话。

选择采用一次input_required表单往返，显式区分accept/decline/cancel/missing。续调携带SDK签名requestState，绑定原方法/工具参数、候选ID及价格快照、有效期和当前已有认证主体；不把它当作Human身份或付款凭据。签名失败、过期、跨参数复用和缺失答复不得重新自动弹表单。只携公开商品信息，不含秘密；用服务端独立运行期随机密钥，重启后旧选择失效并重新明确选择，不新增持久化搜索/选择表。相同已有Demo凭证不声称能区分不同真实人。接收后仍重新查目录与库存，状态签名不能代替当前约束校验。

实现前先核实正式包版本、迁移范围与Apps扩展peer依赖；有必要的兼容v1传递依赖须记录，不能把Apps依赖残留误报为服务端未升级。若实际必须改变身份/购物授权、增加持久会话或新服务，则按项目规则呈交具体差异；SDK升级与上述无状态新协议适配已获授权，不重复申请。真实Host不支持时记录阻塞，不把SDK测试成功冒称Host点选通过。不得恢复旧T-07最终付款授权设计。

## Risks / Trade-offs

- 简繁转换多义字/词表过宽 → 明确可支持的等价术语，正反例同时验收，不扩展硬约束；必要时缩小别名范围而不是静默误匹配。
- 单卡目标过多仍很长 → 5组上限、每组4项、组内分页；不隐藏失败目标或无限增加iframe高度。
- 新旧Host缓存混用 → 支持旧单Page、新grouped显式解析、资源版本升级及重新发现，精确白名单兼容，真实Host单列证据。
- 同时进行的紧凑卡片修复与结算Spec收尾 → 保持独立分支/Change，实施前对齐已合并版本；归档本Change前先同步前序Spec，避免旧购买契约复活。
- 客户端协议/交互能力未知 → 在候选选择实现前先做只读往返实验，SDK升级和无状态新协议适配已授权；额外持久会话/身份架构变更另行确认；失败时保留对话澄清，不以SDK替身替代真实点选。
- 当前仍无实现证据 → 独立规划审查及修订复核完成，Human已授权审查后实施；规划通过不等于运行通过。

## Migration Plan

1. 审查本提案并确认默认边界、单目标兼容、支持语言范围；在既有Decision/Baseline中仅传播实际批准差异，不整体标记Approved。
2. 完成候选选择的协议/Host可行性实验；升级SDK并实现已授权的新协议无状态路径；额外协议会话变化先明确裁决。对齐前序Change及紧凑UI最终版本，先共享匹配/契约，再批量服务及工具，最后共享分组UI；不迁移数据库或清理任何业务数据。
3. 同步API/Apps资源与schema，保留单查询Page；升级资源号、缓存别名、Bridge校验和交付资源检查，刷新Host发现。回退需成套回退协议与资源并提示批量卡片不可用，不把未知kind误读为单目标。
4. 隔离HTTP/MCP、SDK替身、真实Host分层验证后呈交Human验收；先完成前序正式Spec同步，再审本Change合并预览和归档。提交、合并、Push与发布分别核对授权。
