# Design

**本次修订状态：Approved Planning（2026-10-30）。** 独立规格审查无重要 Finding，Human 明确“批准当前修订版，提交之后开始实施”；批准来源与权限见 Proposal。原 S5 实施证据见 Tasks，§4 为本轮已批准、待实施的替代契约。

## Context

Approved Planning（2026-10-30），批准依据与授权范围见 proposal.md。以下实现现状为规划时观察：cart/commands.ts 是无 React 的同源 HTTP 函数，CartProvider 协调建车材料、同页锁与未知结果；CartService.replace 锁车后校验权限/版本/完成状态并保存，来源原先固定不变。现有统计直接 count(origin=AGENT)，来源转换后不能继续这样推导创建事实。规划时尚无 WebMCP Adapter。

全局依据为 Approved Requirements v0.2、Product Design v0.2 和 Technical Design v0.5；来源转换是本轮明确增量。现有 agent-shopping 正式 Spec 只约束经过服务认证的基础 MCP，其创建/编辑规则不因 WebMCP 扩展改变。

## Goals / Non-Goals

**Goals:** 页面工具复用 Commands 与业务用例；转换原子、报价一致、旧确认失效；可独立核对真实浏览器/Host；保护既有有效创建统计。

**Non-Goals:** S6、Agent 自动提交购买、额外身份认证服务、通用工具框架、跨入口实时推送、公开部署或新增长期恢复权限。

## Decisions

### 1. 显式页面工具入口，业务用例共用

采用 imperative WebMCP Adapter，按页面注册并用生命周期取消机制清理。搜索工具更新 URL，由现有页面查询渲染，不额外并行取同一列表；详情/评论复用公开查询。购物工具调用普通 Commands，页面提供选择车、忙碌/草稿检查、刷新与导航回调。Adapter 不调用 Hook、不模拟 DOM 点击，不独立持有购物车 Store。工具名与精确 schema 在实现时按页面用途细化，不照搬服务器七工具。

替代方案：DOM 自动点击不能提供本轮要求的明确工具入口；另建 WebMCP 服务与已有前端能力重复；统一跨协议 Registry 无当前需求。

### 2. 来源通道与认证边界

已实施同源 `/api/v1/webmcp/carts` 创建及对应 `/:id/items` 整车编辑通道；本次增加 §4.1 的逐项操作通道，保留旧路径兼容。Controller 固定 AGENT 意图，复用普通浏览器车 Cookie、Origin/JSON 防护、建车证明/幂等与 CartService，不放行请求任意 source/origin 或报价。普通 `/carts` 行为保持。WebMCP 建车采用浏览器每意图证明命名空间，不借用基础 MCP 的全服务 principal 或把其秘密下发。

采用独立路由是为区分业务意图、审计和校验，不构成防伪认证：浏览器代码、请求路径或自定义 Header 均可被模拟。Human 已明确不要额外身份依据，并在获知可模拟限制后将来源防伪列为后续规划目标，本轮不做。按 D-07 S5 补充与 SEC-02 限定记录当前边界，不再将此项作为 S5 规划阻塞，也不能声称已防止模拟工具请求。替代“仅发送 source=AGENT”缺少清楚的普通/WebMCP 契约边界；服务秘密进浏览器不可接受。

### 3. 原子转换与报价/确认

WebMCP 成功写入在 Cart 事务与现有行锁内检查有效车权限、锁后期限、未完成、预期版本及操作后的完整条目，再一次写入 items、origin=AGENT 和递增版本，返回同一服务端报价。首次转换即使数量未变也递增版本；普通编辑不降回 HUMAN。搜索、读取、注册和失败不升级。合法清空编辑可转换来源，但空车无报价、不增加创建统计。

同车成单与转换使用既有锁及唯一订单约束：订单先提交则拒绝转换；转换先提交则旧版本确认失效。Human 必须重新审阅新报价并新点击；不把来源变化局限为总额变化。保留原 cartId、createdAt、handoffIssuedAt、凭证及权限截止。

### 4. 电商逐项操作、服务端权威与按场景刷新（本次拟议修订）

本节在修订版获批后替代 D-23 对应的 Web 整车编辑与仅手动刷新细节；服务端版本权威、不覆盖/合并/重放旧草稿、创建幂等与购买恢复保持。手机/电脑先后访问同一车，靠重新进入/返回时读取和写入时版本裁决校准；不承诺所有设备实时显示一致。

#### 4.1 操作与兼容边界

新增 `POST /api/v1/carts/:id/operations` 和 `POST /api/v1/webmcp/carts/:id/operations`，JSON 严格只接受 `expectedCartVersion` 与一个 `operation`。operation 是以下三种之一（字段外一律拒绝）：

| type | 字段 | 服务端意图 |
| --- | --- | --- |
| `add_item` | productId、quantity（正整数） | 对服务端当前条目增加该数量；不存在则加入 |
| `set_quantity` | productId、quantity（正整数） | 将已存在商品设为这个绝对数量；0 不隐式删除 |
| `remove_item` | productId | 删除已存在的整行；最后一行可删除为空车 |

复用现有 productId、数量及整车数量/条目上限。设量或删除不存在的行返回 `CART_ITEM_NOT_FOUND/409`，不增加版本、不转换来源，客户端要求刷新。新入口按当前 Cookie、精确 Origin、JSON、权限期限和完成状态校验；不接受来源/价格/Token 字段。权限检查先于暴露版本和条目错误。成功返回完整 CartView，不回传局部拼接报价。

服务端在既有 Cart 行锁事务内检查预期版本，再从持久条目应用一次操作、验证整车结构约束与目标行的购买条件，原子写入条目、来源（WebMCP 升级）及递增版本。即使设量与原值相同，成功 WebMCP 操作仍按既有规则升级并使旧确认失效。add_item/set_quantity 必须严格校验目标商品的当前有效性、可购买状态及目标数量库存；remove_item 允许删除失效或缺货行。未触及的既有问题行原样保留，返回完整 issues、报价及 canCheckout=false，不能阻止逐行修复，也不能被视为可购买。任何目标行/结构校验失败整笔回滚，问题条目不自动减量或删除。原整车接口仍按完整结果全有效校验，不悄悄放宽旧契约。加购不预留库存，金额仅服务端计算。

`add_item` 是增量意图，不能因为更容易合并就自动换版本重试。相同 expectedCartVersion 的重复操作最多成功一次；响应未知仅重读，不自动重发，因此本轮不新增操作幂等键、结果日志或重试队列。首次建车继续原 UUID/证明同键幂等恢复，区别于已有车操作。

原 `PUT /carts/:id/items`、`PUT /webmcp/carts/:id/items` 和基础 MCP 七工具保留原契约与版本拒绝；本次 Web 不再使用整车替换。基础 MCP `update_cart` 不改 schema，避免扩大已验收 S4。WebMCP 当前购物车页 `update_cart` 改为 `{expectedCartVersion,operation}`，旧 items 参数明确拒绝，注册描述及 README 同步，Host 须使用重新发现的工具。`add_to_cart(productId)` 保持每次加入一件，已有车改调 add_item；新车仍走原创建通道；工具无购买提交能力。

#### 4.2 Web 交互和单车协调

数量输入保留即时输入体验，在 Enter 或失焦时提交一次合法且已变化的 set_quantity（同次 Enter/失焦不得双发）；不逐键请求、不使用防抖自动换版本保存。移除点击后提交 remove_item；目录/详情点击加入提交 add_item。取消整车“儲存調整”及“尚未保存全车”的提示，显示当前行保存中、成功或可行动错误。输入非法不发请求、保留输入并关联错误，提供恢复服务端已保存数量的显式操作。

同一浏览器当前车仅一个写请求在途，Human、工具和创建恢复入口共用短暂保护；在途时禁用冲突写控件，工具返回 CART_BUSY，不排队、无后台重放。存在未保存数量输入时拒绝其他写意图，先提交、修正或显式放弃该输入，工具返回 UNSAVED_DRAFT。提交后的等待期间禁止产生新的数量草稿，以免成功响应丢失新输入；工具起始后的 Human 输入也由同一保护阻止。成功使用完整服务端快照更新页面，不能只修改一个商品后自行拼总价。

请求结束即释放短暂保护，不因未知结果持有全局锁。冲突、行不存在或响应未知只将相应页面标为需刷新，禁止该页继续写入和进入 Checkout；离开该页不长期锁其他页面。普通输入/商品校验错误可修正后用原版本建立新意图；不恢复原编辑。创建未知保留原创建材料和非敏感标记，沿用既有显式同键重试及刷新丢材料限制。

#### 4.3 读取、失效与响应归属

| 触发 | 行为 |
| --- | --- |
| 首次进入/重新进入车页 | GET 服务端完整 CartView；无当前车时不创建车 |
| window focus、pageshow 或 visibility 恢复 visible | 合并同一轮事件，仅在当前车无草稿、无在途操作、未处于冲突/未知时重新 GET |
| 返回事件遇草稿 | 保留输入，提示需重新加载，不自动写入；显式放弃并 GET 后才继续 |
| 返回事件遇在途操作 | 记一次待校准意图；请求结束后无草稿且无冲突/未知才 GET，防止遗漏这次返回 |
| 冲突/未知结果 | 保持需刷新；用户点击“重新載入購物車（放棄未儲存修改）”后重新 GET，不自动获取新版本后重放 |

后台 GET 在发起后如出现新输入或写操作，响应不覆盖页面；保留新输入，写入后再校准或提示显式刷新。每次显式重新加载建立新页面请求代次，旧 GET/写结果不能修改新代次，即使响应车 ID 相同；换车/卸载同样隔离。Abort 仅节省等待，不被视为服务端取消写入。刷新有请求在途时不假定操作已失败，读取仍可能早于旧请求提交；下一写仍由服务端版本裁决。

所有入口只采用服务端返回版本；同车旧成功响应不得回退最新已收到快照。冲突（可含 currentCartVersion）或未知建立刷新要求后，之前在途成功不得清除该要求；即使只知道发生冲突而没有新快照，也不能把旧成功当作已完成刷新。只有当前代次的有效重新加载才解除。请求代次用于判断本地响应归属，不是业务数据版本，不新增跨端版本算法或客户端合并。

同车所有页面读写复用一个小的浏览器协调边界和现有无 React Commands；不引入 TanStack Query/SWR、新 Store 或通用同步框架。跨标签页、基础 MCP、其他设备仍通过持久服务端状态与版本校验协作；本轮不做 BroadcastChannel、轮询或 WebSocket 推送。

#### 4.4 交易新鲜度与访问边界

CartVersion 仅代表车内容/来源的持久修改，不证明库存、目录价格、优惠或报价仍然有效。GET 返回当次服务端报价，Checkout 沿用既有 review 和 submit 的重新计价、库存事务、quote/purchase hash、独立确认与未知结果恢复；车内容、来源或报价失效必须重新审阅并新点击。购物车页面显示“可前往结账”不是库存保留或成交承诺；完成 Order 为不可被购物车更新改写的成交快照。

没有登录时，手机和电脑不会自然共享 Cookie。只有通过既有有效 Handoff/车能力取得同一 cartId 的权限，才读取同车；不靠版本号、公开车 ID、设备指纹或新身份映射补权限。不新增账户、游客车合并、凭证同步或延长期限。

#### 4.5 取舍和替代方案

- 选择逐项操作 + 按场景读取：减少整车旧快照覆盖意图的风险，代价是新增薄接口和每行保存状态；本页短暂互斥换取明确反馈，不支持离线编辑队列。
- 保留整车显式保存：实现更少，但不同商品的跨端操作更容易相互冲突；仅在旧 HTTP/基础 MCP 保留兼容，不作为新 Web 交互。
- 实时推送 + 自动合并：可降低显示延迟，但无法替代写入和成交校验，且需要新业务合并规则；本轮不采用。

### 5. 有效创建事实保持原口径

建议 Cart 增加不可变 `agentCreated` 布尔事实：迁移前来源不变，历史 AGENT 可据旧 origin 回填 true、HUMAN false；后续只有 MCP/WebMCP 合法非空 Agent 创建写 true，普通创建 false，来源转换不修改。汇总查询此事实，不再依赖可变 origin。原车来源供优惠使用；不改变 agent-cart-metrics 正式 Spec 或声称接手等于创建。无需通用事件表。

### 6. 浏览器与 Host 兼容性先实测

2026-10-30 核对的官方文档使用 `document.modelContext`；注册清理由 signal 管理，旧 navigator API/注销接口不能直接照抄。实现前记录实际可用 Chromium/Host 及 API 版本，功能检测且仅在有效页面能力就绪后注册。没有所需环境时保留未验证状态，不用 polyfill 或测试扩展模拟成功替代真实 Host 验收；不因官方支持 Chrome 就假定当前 Codex 工具链可调用。

来源：[Chrome WebMCP](https://developer.chrome.com/docs/modern-web-guidance/guides/webmcp/webmcp)、[Imperative API](https://developer.chrome.com/docs/modern-web-guidance/guides/webmcp/agentic-javascript-tools)、[规范草案](https://webmachinelearning.github.io/webmcp/)。API 仍需以实测版本锁定，当前未运行浏览器验证。

## Risks / Trade-offs

- 无独立调用者证明 → Human 已将来源防伪后置，限定记录见 D-07 S5 补充；本轮保留既有权限防护，Origin/专用路由不能证明 Agent 身份。后续扩展部署或信任边界时重访。
- 普通车升级影响金额、确认与创建统计 → 事务/并发反例及独立不可变创建事实，使用真实 PostgreSQL 验证。
- 浏览器/Host 尚未确认可用 → 实现首项能力预检；具体支持结论留真实证据，不提前承诺兼容。
- 组件共享协调易遗漏脏草稿或迟到响应 → 保留页面状态所有权，桌面/移动回归并验证切车/离页。

## Migration Plan

先完成 Planning Review、Human 整体批准、提交授权与高风险规划 Checkpoint，再进入实施。S5 原迁移只新增/回填创建事实，保留 Cart/Order/Inventory；不 seed 或清理。验证迁移前后创建统计一致。本次逐项操作修订不新增数据库迁移；先部署兼容旧路径的新 API，再更新 Web，回退 Web 时保留新 API/数据即可，不改订单、来源或创建事实。

来源转换上线后不能直接回退到仅按 origin 统计的旧版本；回退前停用 WebMCP 新写入口并保留来源及创建事实，使用兼容旧数据的应用修订，不把已获优惠车批量降回 HUMAN。完成订单快照不改写。全局基线的限定补充与正式 Spec 同步按批准/验收阶段处理，不先改历史归档。
