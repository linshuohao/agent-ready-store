# shopping-cart Specification

## Purpose

让顾客把商品选择保存为可恢复、可编辑且受车级权限保护的购物车，避免建车重试和并发编辑破坏购买意图，并为后续独立确认及订单流程提供一致输入。

## Requirements

### Requirement: 创建与数量校验

系统 SHALL 按唯一商品 ID 和正整数数量创建普通购物车，数量不得超过当次运行库存；拒绝未知、不可购买商品及重复 ID，不能按名称合并、静默减量或部分接受。普通 Web 可创建空车。创建与编辑 MUST 不预留或扣减库存。

#### Scenario: 有效创建与非法输入
- **WHEN** 普通 Web 提交有效条目、空条目或包含无效数量/重复 ID/不可购买商品的条目
- **THEN** 有效整车或空车创建成功；非法整车被明确拒绝且不留下部分 Cart，库存始终不变

### Requirement: 持久编辑与冲突

系统 SHALL 读取持久化购物车，浏览器按预期版本提交一次加购、设量或移除操作；原 HTTP 与基础 MCP 整车替换契约保持兼容。服务端从持久条目应用操作，成功编辑原子递增版本；普通编辑保留来源，WebMCP 成功编辑允许在同一事务内将 HUMAN 转为 AGENT，旧版本编辑明确冲突。已有条目因库存减少或商品失效而受阻时 MUST 保留内容供调整；编辑可以删除问题条目，不能自动覆盖其他修改。

#### Scenario: 同车并发编辑
- **WHEN** 两个请求使用同一预期版本提交不同条目
- **THEN** 最多一个成功，另一个得到版本冲突；最终条目与成功版本一致，无丢失更新

#### Scenario: 库存下降与删除问题条目
- **WHEN** 已有数量超出当前库存或商品失效，顾客读取后逐项修正，或通过旧接口提交有效整车
- **THEN** 读取保留原条目并说明问题；单操作严格验证目标行的新数量/可购买性及整车结构，未触及问题行原样保留并阻止结算，删除可逐条修复多个问题；旧整车接口仍要求完整结果有效，校验失败整笔拒绝且原车不变

#### Scenario: WebMCP 来源转换与失败原子性
- **WHEN** WebMCP 使用正确版本成功编辑 HUMAN 车，或编辑校验失败/事务回滚
- **THEN** 成功时条目、AGENT 来源和版本一起提交并重算报价；失败时不发生部分转换，重试不得覆盖新版本

### Requirement: 创建幂等与恢复

系统 SHALL 将创建请求绑定到有效创建证明、请求键和原始条目；同证明、同键、同内容重试只创建同一车，返回当前车及相同访问能力，不重放原条目覆盖后续编辑。已有请求恢复 MUST 不以原条目仍满足当前建车条件为前提；库存或目录变化通过当前车的问题反馈，访问权限仍须有效。异内容或无有效证明 MUST 拒绝。服务重启及响应丢失不能破坏持久幂等。

#### Scenario: 响应丢失及编辑后重放
- **WHEN** 建车已提交但响应丢失，服务重启后持原证明重试，或该车编辑后再重试原请求
- **THEN** 仅有一个 Cart，恢复原访问能力及当前内容，后续编辑不被还原

#### Scenario: 不同请求或伪造恢复
- **WHEN** 同键异内容重试、并发提交同一请求，或只凭 cartId/requestId 请求恢复
- **THEN** 异内容和无证明恢复被拒绝；同请求并发最终仅一车，秘密不能被其他调用者领取

#### Scenario: 创建成功后购买条件变化
- **WHEN** 建车成功但响应丢失，原商品随后库存不足、售罄或从目录失效，服务重启后持有效原证明和相同请求重试
- **THEN** 恢复同一车的访问能力和当前内容，按当前商品/库存返回问题与报价，不因原商品已不满足新建条件而拒绝恢复，不创建新车且不改变库存

### Requirement: 车级访问与可信来源

系统 MUST 在读取和编辑时验证目标车能力；公共 cartId、另一车凭证及 MCP 服务凭证单独出现均不授予访问权。普通 HTTP 创建来源固定 HUMAN，MCP 与注册 WebMCP 工具创建固定 AGENT；WebMCP 成功编辑允许 HUMAN 原子转为 AGENT，Human 后续编辑保留 AGENT 及优惠资格；拒绝普通请求的 origin/source/价格等越权字段。WebMCP 入口按本轮 Human 决定不另设 Agent 身份认证，不声称其浏览器入口为服务端身份证明。写请求须通过同源与请求伪造防护。秘密不得进入 URL query、公开响应、日志或持久客户端缓存；受保护的 MCP 创建结果与明确 Handoff 链接是专用凭证交付通道，普通 CartView 和错误不含秘密。

#### Scenario: 错车与来源伪造
- **WHEN** 使用 A 车凭证访问 B 车，或普通创建请求伪造 AGENT 来源/商品价格
- **THEN** 访问或输入被拒绝，B 车不变且不能获得 AI 专属优惠

#### Scenario: 跨站与多车
- **WHEN** 跨站请求尝试写车，或同浏览器两个标签分别操作 A/B
- **THEN** 跨站写被拒绝，A/B 权限与内容互不覆盖；失败响应不泄露车内容或秘密

#### Scenario: WebMCP 优惠与访问能力分离
- **WHEN** 已注册工具创建车或接手编辑普通车
- **THEN** 成功后适用 AGENT 优惠；接手仍需原车合法权限，不凭工具入口或 cartId 取得他车权限，转换不延长有效期

### Requirement: 固定访问期限

系统 SHALL 对未交接Human/Agent Cart采用服务端成功创建记录起固定24小时的访问期限；到期等号失效，读取、编辑、失败、重试及Cookie重设均不能续期或恢复过期权限。系统 MUST 不因访问失效删除Cart、修改库存或推导长期订单查询权。有效期内首次分享后统一改为首次分享起完整24小时，重复分享不续期；首次分享须验证同车能力、未完成事实及锁后当前时间，所有持有者共用该期限。

#### Scenario: 创建期边界与重试
- **WHEN** 对尚未首次分享的车，在创建截止前、截止等号或截止后读取、编辑或持原创建材料重试
- **THEN** 截止前按有效权限处理，截止等号及之后明确失效，不改原createdAt或补发新权限；Cart和Inventory内容不因期限校验改变

#### Scenario: 等待写锁期间到期
- **WHEN** 编辑请求到达时尚有效，但等待Cart写入锁后已达到当前统一截止时刻（未分享为创建起24h，已分享为首次分享起24h）
- **THEN** 服务端以锁后当前时间拒绝编辑并保持原内容，不以请求到达时间或客户端计时放行

#### Scenario: 分享后跨创建截止仍可编辑
- **WHEN** 车在创建后第23小时首次分享，编辑等待车锁跨过创建后第24小时，但锁后尚未达到首次分享后第24小时
- **THEN** 不以原创建截止拒绝；在有效车凭证、版本及条目校验通过时允许保存，统一截止仍为首次分享起24h，不因编辑续期

#### Scenario: 首次分享阶段切换的后续兼容
- **WHEN** 在创建截止前首次分享，或在创建截止等号及之后尝试首次分享
- **THEN** 前者保证首次分享起完整24小时，不被创建截止时间截短，后者拒绝；S4新增运行证据，不能反推S2当时已实现分享

### Requirement: Web 加购与购物车编辑

系统 SHALL 提供列表/详情轻量加购反馈和独立购物车页；加购不强制跳转。用户修改数量后在 Enter 或失焦时逐项保存，点击移除立即请求，无整车保存按钮；可见当前报价、加载、空车、访问失效、保存失败和冲突状态。切换车或请求乱序时 MUST 不混入别车内容或静默覆盖新输入；用户明确重新加载时可放弃全部未保存修改；可购买车提供进入 Hosted Checkout 的入口，进入或编辑均不代表购买确认。已完成车展示原结果入口并禁用编辑与再次购买。

#### Scenario: 加购与连续编辑
- **WHEN** 顾客加购、进入购物车、改量、删除至空车或遭遇保存失败/版本冲突
- **THEN** 加购结果明确可见，合法已变化数量在 Enter 或失焦时只提交一次，不逐键提交；移除直接提交，成功后展示完整服务端结果；输入校验失败不请求且保留输入并提供恢复已保存数量操作，版本冲突或响应未知提供明确重新加载路径，不自动重放覆盖

#### Scenario: 首次跨商品快速加购
- **WHEN** 尚无当前车，顾客点击商品 A 后在创建返回前尝试点击商品 B
- **THEN** 当前页面所有加购入口在同一创建期间均不可再次提交，第二次点击不被接受或显示成功；A 创建成功后恢复入口，顾客可将 B 加入同一车，不因两个入口分别建车

#### Scenario: 加购请求结果未明
- **WHEN** 创建响应丢失但原材料仍在，或已有车编辑响应丢失
- **THEN** 创建仅允许原材料同键显式重试；编辑提示重新加载查看服务端结果，不自动重读比较或重放，不长期锁住其他编辑

#### Scenario: 编辑冲突与重新加载
- **WHEN** 保存遇版本冲突，用户选择重新加载
- **THEN** 提示服务端状态已更新；重新 GET 后以完整服务端内容替换快照和全部草稿，不展示差异、不合并、不自动保存；新请求仍携所读版本

#### Scenario: Human 与工具成功响应乱序
- **WHEN** 旧页面或已结束等待的写请求成功响应迟到，而新页面已收到同车更新版本
- **THEN** 旧代次结果不影响当前页，同车低版本不回退快照；后续操作只能携服务端返回的版本，不自行递增版本或换版本重放旧草稿

#### Scenario: 先到冲突与迟到成功
- **WHEN** 页面先收到版本冲突或未知结果，随后收到更早发起请求的成功响应
- **THEN** 继续要求显式重新加载，不将旧成功视为刷新，不解除写入/结账限制；只有当前代次的有效重新加载才解除要求

#### Scenario: 页面刷新与响应归属
- **WHEN** 创建成功后刷新原车，或 A 车请求迟于切换到 B 后返回
- **THEN** 有效 Cookie 可读取原车，A 响应不能覆盖 B；敏感响应不被共享缓存

#### Scenario: 响应前丢失创建材料
- **WHEN** 建车响应和 Cookie 均未送达，浏览器刷新导致原创建材料丢失
- **THEN** 明确显示创建结果无法确认，不凭公开ID补发权限或自动重建；Human已在本轮接受此恢复限制，长期恢复能力仍不在S2内

#### Scenario: 刷新后的非敏感待确认标记
- **WHEN** 创建请求发出后结果未明，顾客刷新丢失内存材料
- **THEN** 标签页保留不含Token、请求键或条目的待确认标记，显示结果无法确认并阻止新写意图；用户明确重新发起后才允许新建。成功确认或明确拒绝会清除标记，网络与服务故障不会清除；内存材料仍在时继续原请求重试

#### Scenario: 基本可访问性
- **WHEN** 在桌面/移动宽度以键盘编辑购物车
- **THEN** 输入有标签、错误关联输入、反馈可被辅助技术感知、焦点可见且保存失败后可继续操作

#### Scenario: 全站固定购物车入口与空状态
- **WHEN** 顾客在任意页面滚动或尚未加购便进入购物车
- **THEN** 视口顶部Header保留购物车入口；没有当前车时直接显示空状态，不在进入网站或读取空页时自动创建持久Cart，首次加购才创建


#### Scenario: 读取旧版本后原编辑提交
- **WHEN** PUT 响应丢失，显式刷新读取旧版本，原 PUT 随后迟到提交
- **THEN** 不根据旧读取判定失败或重放原操作；下一次用户新编辑仍携读取的版本，由服务端拒绝过时写入并要求再次重新加载

#### Scenario: 恢复期间其他入口编辑
- **WHEN** PUT 结果未明，另一入口先递增版本
- **THEN** 用户重新加载取得当前服务端数据，不比较原条目、不声称原请求从未成功、不自动改版本重发

#### Scenario: 冲突后最新车删除或新增商品
- **WHEN** 保存遇冲突，最新车已删除、新增商品或清空，用户明确重新加载
- **THEN** 整体放弃原草稿，展示完整最新车或空车，不展示两份内容、不合并或保存隐藏条目；在最新数据上重新调整

### Requirement: 成功车只读与结果标记

系统 MUST 从同车唯一订单事实识别已完成车；有效车权限内读取和创建重放返回当前完成标记及原订单定位，不能恢复旧条目或重新建车。完成后所有编辑请求拒绝，canCheckout=false；普通读取不生成新确认材料，完成事实不能通过陈旧客户端版本解除。

#### Scenario: 成单与编辑竞争
- **WHEN** 同车编辑与提交并发
- **THEN** 编辑先完成则旧版本提交被拒绝，提交先完成则编辑被拒绝；不存在成单后改变原车或再次购买

#### Scenario: 成功后创建重放
- **WHEN** 在有效权限内重放已完成车的原创建请求或读取原车
- **THEN** 返回同车完成标记和原订单定位，不重置完成状态、不覆盖条目、不重新计算历史成交金额；当前估价如展示必须与成交快照明确区分

### Requirement: 单项购物意图与兼容

系统 SHALL 在浏览器逐项提交加购、设定数量和移除操作，每次仅一个操作并携所读服务端版本；不接受客户端整车快照作为新操作的来源。成功返回完整 CartView，失败不部分更新。旧 HTTP/基础 MCP 整车替换行为 MUST 保持兼容，不能因新交互改变旧调用参数或版本拒绝。

#### Scenario: 手机加购后电脑加入其他商品
- **WHEN** 两端已合法访问同一车，手机加入 A 后电脑重新读取并加入 B
- **THEN** 服务端保留 A 并加入 B；电脑仅提交加入 B 的意图。电脑使用旧版本则明确冲突，不静默换版本重试，不删除 A

#### Scenario: 增量与绝对数量不同
- **WHEN** 加购一个已存在商品、设定已有商品的绝对数量、删除最后一行，或设量/删除不存在的行
- **THEN** 分别增加请求数量、设为请求数量、变成无可购买报价的空车；不存在行返回明确错误并要求刷新，不能变成隐式加购；数量为 0 不作为删除

#### Scenario: 多条旧问题商品逐行修复
- **WHEN** 已有车包含两条或更多缺货/失效商品，顾客逐条删除或将目标数量修正为可购买数量
- **THEN** 允许每次有效单行修复，其他问题行原样保留且完整反馈；只要仍有问题 canCheckout=false，不能自动移除其他问题商品或放宽目标商品校验

#### Scenario: 重复投递与未知结果
- **WHEN** 同一操作以同一预期版本重复到达，或响应丢失
- **THEN** 同版本最多成功一次并递增版本，另一次明确冲突；客户端未知时仅显式重新加载，不自动重发增量操作，也不自动替换版本再次提交

#### Scenario: 同车短暂互斥与输入校验
- **WHEN** 当前车存在在途写入或未保存数量输入，其他 Human/工具入口又尝试写入
- **THEN** 在途时返回忙碌且不排队；未保存输入须先提交、修正或显式放弃，其他写入拒绝。请求期间不能产生被响应覆盖的新草稿；请求结束释放短暂互斥，冲突/未知仅限制受影响页面直至重新加载

### Requirement: 按购物场景校准快照

系统 SHALL 在进入购物车及返回前台时校准服务端快照；有草稿、在途操作或需显式刷新的状态时不得静默覆盖。版本由服务端维护，页面快照允许暂时过时；CartVersion MUST 不被当作库存、价格和优惠仍有效的保证。Checkout 与成单继续独立验证交易条件和 Human 确认。

#### Scenario: 电脑旧页返回前台
- **WHEN** 手机已修改同车，电脑重新进入车页或旧页回到前台且无草稿、无在途请求、无冲突/未知
- **THEN** 读取并展示服务端完整当前车和报价；同轮多个返回事件不重复查询，无需跨端推送也能校准

#### Scenario: 返回期间有输入或请求
- **WHEN** 返回前台时有草稿、在途操作，或后台读取发起后用户开始输入/写入
- **THEN** 草稿不被读取结果覆盖，提示显式重新加载；在途操作结束后条件允许再校准一次。旧读取或旧页面响应不能重启旧内容或清除刷新要求

#### Scenario: 车版本未变但交易条件变化
- **WHEN** 车内容版本未变，库存减少、商品失效或报价/优惠发生变化后进入 Checkout
- **THEN** 服务端重新验证当前可购买条件；不符合条件则阻止成交，购买内容或报价失效须重新审阅并新点击；完成订单保留原成交快照，不被车页刷新改写

#### Scenario: 非登录设备访问同车
- **WHEN** 手机和电脑未登录且各自只有本机 Cookie，或第二设备经有效 Handoff 获取同车权限
- **THEN** 前者不自动识别/合并购物车，也不凭公开 ID 访问他车；后者在原权限期限内读取同车；本轮不新增账户、游客车合并或凭证同步
