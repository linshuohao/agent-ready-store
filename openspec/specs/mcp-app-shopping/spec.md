# mcp-app-shopping Specification

术语说明：Agent接入分为 MCP 与 WebMCP。MCP Apps 是 MCP 的交互式 UI 增强，复用现有 MCP Server、连接和业务用例，不构成额外入口或路径。支持 Apps 的 Host 展示内嵌 UI；不兼容时降级为 MCP 文本与结构化结果。降级保留可用工具能力；购买仍遵循适用契约与Human确认要求，不能把文本返回视为完整购买验收通过。当前订单生命周期目标由网页订单入口承接无 Apps 时的Human支付，实际可用性须验证。验收覆盖 MCP 的 UI 增强与无 Apps 兼容模式，以及 WebMCP 页面工具。

## Purpose

使支持MCP Apps的Host通过隔离静态资源和Bridge运行与Web共用的购物应用，按搜索目标汇总展示、按完整购买意图展示最终订单并由Human内嵌支付；保留上下文恢复、公开数据边界及能力不足时的明确降级。

## Requirements

### Requirement: Apps资源与公开展示
系统 SHALL 提供可发现的隔离静态UI资源并关联实际步骤工具结果；静态资源无交易数据、运行时凭证或私有商品字段。动态视图展示服务端公开商品、车版本/条目/预估及订单固定快照，不执行商品评论脚本或指令，不客户端计算优惠。不支持Apps的Host可使用新基础MCP，不承诺旧七工具schema兼容。

#### Scenario: 资源加载和公开数据
- **WHEN** Host读取合法资源、未知资源或无有效服务认证请求资源
- **THEN** 分别返回静态视图、明确错误或拒绝，不读取任意文件；商品同名不合并，问题条目可见，已有订单不使车只读

#### Scenario: 内嵌搜索结果与垂直区块布局
- **WHEN** MCP Apps展示搜索结果、商品详情、购物车或订单等内嵌页面
- **THEN** 目录直接展示搜索结果，不渲染搜索或筛选表单；内嵌页面各主要区块纵向排列，不采用左右分区；搜索商品卡片可按可用宽度并排，窄视图自动减少列数，图片保持紧凑高度而不随整行宽度放大；普通Web保持现有搜索和响应式布局，继续使用同一共享应用

#### Scenario: 按意图只展示最终结果
- **WHEN** 用户明确购买，或只要求搜索商品
- **THEN** 购买准备使用无UI的query_products及详情/购物车/报价工具，同一次购买完整集合只调用一次create_order生成包含全部商品的一张最终结算卡片（Human明确拆单除外）；搜索使用search_products生成一张搜索结果卡片；支付与状态恢复在原结算卡片更新，不生成中间工具卡片、不自动外跳

#### Scenario: Host缓存最终卡片旧URI
- **WHEN** 已认证Host读取此前公布的search-products或create-order的v4/v5/v6资源URI
- **THEN** 精确映射至当前最终卡片静态HTML，响应保留请求URI；资源列表仍只公布两份当前资源，不恢复旧中间卡片或接受任意版本/文件路径；工具发现缓存仍需Host刷新，不视为UI真实呈现证明

### Requirement: Bridge适配与上下文接续
Apps SHALL 经所属服务Host Bridge调用共享购物/订单能力，不直接获取网站Cookie或服务Token，不依赖Next环境。按cartId/orderId恢复Demo上下文，不索取车Token；视图目标与当前购物车分开，分享只展示单订单。资源不申请无关权限，外链只接受固定可信站点及预期订单路径。

#### Scenario: 旧卡片与重新挂载
- **WHEN** Host重新投递旧订单卡片、视图重挂载或恢复原工具结果
- **THEN** 读原orderId及当前事实，不新建Review/订单、不延长预留、不自动支付；缺少目标ID时明确无法恢复，不猜测新车

#### Scenario: 不同车接续及非法链接
- **WHEN** 当前车A时打开B订单，或Host提供非法数据/非预期外链
- **THEN** 先只看B订单，继续B购物才明确确认接续，不合并覆盖A；非法结果拒绝使用，不执行内容或导航

### Requirement: Apps购物与局部协调
Apps SHALL 支持明确加购、整行选购、设量和移除，使用原版本及操作请求键；草稿期间不覆盖输入，冲突显式刷新，未知恢复原请求而不换键重放。订单待支付不锁车，多个订单可独立导航；当前视图销毁不撤销服务端在途动作。

#### Scenario: 并发编辑及迟到响应
- **WHEN** 外部先改车、低版本结果迟到、重载中尝试写入，或A响应到达B视图
- **THEN** 冲突明确反馈，不覆盖草稿或高版本/其他车；同车读取/写入短暂协调，旧代次不解除新请求busy，未知保留原目标恢复

### Requirement: 内嵌订单支付与分享
Apps SHALL 在生单后直接显示原orderId完整固定摘要和待支付状态，Human点击后经UI专用Bridge直接支付并原地显示结果，不通过Agent消息接续或公开支付工具。Apps专用生单入口计本单AI资格；创建/查询含普通及分享入口，显式分享才使用单订单展示，不自动外跳支付。

#### Scenario: 模型停止及支付未知
- **WHEN** Agent停止或消息不可用，Human点击支付，随后响应丢失或卡片重挂载
- **THEN** 支付仍可完成；只读恢复原单，明确重试仍同ID，未支付不显示成功；不能把迟到待支付覆盖PAID或把本地到期覆盖在途成功

#### Scenario: 分享及Host拒绝
- **WHEN** Human显式分享有效待支付单，或Host拒绝打开入口
- **THEN** 分享页面仅该单且可由Human模拟支付，无车入口/其他订单/取消操作且不改变当前车指针；失败保留原单和入口，不新建不续期，不把展示限制描述成访问控制

### Requirement: Apps真实Host验收
系统 MUST 记录真实Host版本、协议/SDK、应用revision、资源隔离、Bridge调用、内嵌摘要、Human支付及多单/旧卡片恢复；显式分享另记。替身Bridge、自动化与真实Human分别记证，不绕过Host限制或自动发布公网。

#### Scenario: 可用及能力缺口
- **WHEN** 在真实Host完成购物闭环，或资源/Bridge/内嵌支付不可用
- **THEN** 前者核对同单快照、预留、一次支付和库存；后者保留失败环节并交Human判断，不以基础MCP成功代替Apps验收

### Requirement: Web与Apps完整应用复用
系统 SHALL 让Web和Apps使用同一商品列表/详情/评论、购物车、订单列表/详情、基础控件、样式和资源，以及完整购物流程与交互协调；不得在Apps另写对应界面、样式或购物状态机。环境仅适配HTTP/Bridge、导航、存储及工具结果接续，保留Human专用支付。

#### Scenario: 同一功能跨环境运行
- **WHEN** Web或Apps展示同一实体并执行选购、生单、支付、取消、继续购物及未知结果恢复
- **THEN** 消费同一页面、控件、CSS和流程，仅请求通道及导航/存储由环境适配，草稿保护/错误/终态规则不分叉

#### Scenario: 内嵌导航和显式分享
- **WHEN** Apps从工具结果接续、重挂载、浏览商品或Human显式分享订单
- **THEN** 按原ID读取并在共享应用内导航，显式分享才请求Host打开固定可信订单入口；不自动创建/支付或切换不同车，不直接访问网站HTTP

### Requirement: 同一卡片按搜索目标分组
Apps SHALL 将一次批量搜索的全部目标放在一张卡片，按输入顺序纵向排列各组标题、条件摘要、数量/状态和商品结果；组内使用共享商品卡片的紧凑响应式网格，不强制每行仅一件。首次每组默认4项，通过组内分页访问其余结果，不为减少高度隐藏整个目标或自动另开卡片。

#### Scenario: 两目标及窄窗口
- **WHEN** 结果含耳机、水杯，或Host改变iframe宽度
- **THEN** 两目标都可在同一卡片内找到，宽窗口商品并排、窄窗口自动减列，无横向溢出；完整商品名、价格和可购状态可读，不要求所有结果在一屏内同时容纳

#### Scenario: 空组与重复商品
- **WHEN** 某组没有结果，或同一商品匹配多个组
- **THEN** 空组仍显示目标及无匹配状态；同商品在各相关组各展示一个引用，均指向同一ID及摘要，不把重复展示当不同SKU或自动增加购买数量

### Requirement: 分组内导航重试与结果隔离
Apps SHALL 使用无UI查询在原卡片内更新组分页/重试，保留其他组、目标条件和详情返回位置；按搜索集合、组ID及请求序号隔离响应，旧响应不得覆盖新目标或新页。查询条件不是购买凭证，来自Host/存储的数据须校验，文本不执行HTML或指令。

#### Scenario: 单组下一页及迟到响应
- **WHEN** 耳机组翻页过程中切换目标，或上一页响应迟到
- **THEN** 不覆盖新的搜索集合/页，水杯组状态不被重置；请求失败显示该组可重试状态，不把失败页标为已加载

#### Scenario: 详情返回及重新挂载
- **WHEN** 在某组打开商品详情再返回，或Host重新挂载卡片
- **THEN** 有有效原目标上下文时按原查询及各组页码重新读取当前事实，不重放交易；上下文缺失时明确无法完整恢复并请求重新搜索，不猜测目标、不自动建车

### Requirement: 批量结果协议兼容与真实Host证据
Apps SHALL 明确校验单目标Page和批量grouped两种结果，未知kind或引用缺失不能被当成空成功。资源升级时保留明确支持的旧单目标结果映射，不将批量结果投递给无法解析的新旧混合资源。验收分别记录数据工具无UI、一次展示调用、实际卡片数量及Host版本；不支持Apps时保留分组文本/结构化结果，不称为Apps展示通过。

#### Scenario: 新旧资源切换
- **WHEN** Host缓存旧工具目录或旧卡片结果，或刷新后调用批量展示
- **THEN** 旧合法单查询仍可读取，批量结果使用兼容的资源；能力不足有明确提示，不丢组、不把解析失败降级成无匹配

#### Scenario: 真实多目标搜索
- **WHEN** 在目标真实Host执行包含简繁/英文术语的两个目标，并进行组内分页和详情返回
- **THEN** 记录完整目标、调用轨迹、一张实际卡片及分组恢复结果；SDK替身通过不能代替Human确认，模型多次展示产生多卡必须记为失败或明确未解决限制

### Requirement: 候选选择表单与Apps展示独立
Apps结果卡片 SHALL 与客户端原生选择界面区分；候选选择工具不关联额外Apps资源，不要求为每个候选再展示一张卡片。一次搜索仍汇总展示，明确购买目标解决后只由生单展示最终结算；不支持elicitation的客户端仍可通过对话澄清，不影响已有Apps浏览与Human支付。

#### Scenario: 先选型号再结算
- **WHEN** Human在客户端选择界面接受型号并继续原购买意图
- **THEN** 不逐候选生成Apps卡片，最终结算包含完整目标；选择界面由Host决定且不承担支付确认，Human仍在原结算卡片点击付款
